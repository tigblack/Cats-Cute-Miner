# Playable integration points: Cat Miners (CatOutpostV2), read-only investigation

Paths are relative to `/mnt/claude-data/sargsyan-tinote/cats-cute-miner`. I modified no project files and wrote no scratch files.

## 0. Short answer

The project already contains a pattern that fits a separate playable build almost exactly. The `CatMiners.DevTools` code library (`Assets/Game/Scripts/DevTools/CatMiners.DevTools.asmdef`) is only compiled in when a flag is set (`defineConstraints: ["UNITY_EDITOR || DEVELOPMENT_BUILD"]`). It attaches itself to the game at startup (`OutpostDevPanel.cs:20-27`) without the main code ever referencing it.

**Recommendation:**
- Create a new code library `CatMiners.Playable` that only compiles when the build flag `CATMINERS_PLAYABLE` is set.
- Set that flag only in a new build method `BuildWeb.Playable()`, using `BuildPlayerOptions.extraScriptingDefines`.
- Reuse the `CoreGame` scene. No new scene is needed.

**What the main game already allows without any change** (static override fields, `OutpostController.cs:19-21`):
- `FileSystemOverride`: a storage replacement, so the playable can keep saves in memory only.
- `SaveDirectoryOverride`: a separate save folder.
- `ClockOverride`: a replacement clock, which allows pause or speed-up.

The playable can also use these existing public functions as they are:
- `Hud.Toast`, `Hud.Modal`, `Hud.PollBackButton`
- `IOutpostGame.ContinueToNextMine`, `DismissOffline`, `EventPresented`
- `Board.Cue`, `OutpostDialog.Create`, the `PixelUi.*` building blocks, `TutorialHint.Create`

**Main-game changes that are still needed** (each is off by default):

| # | Where | What |
|---|---|---|
| H1 | `OutpostController.cs:112` | Optional hook that swaps in the playable balance: `public static Func<OutpostConfigSet,OutpostConfigSet> ConfigsOverride;` then `Configs = ConfigsOverride?.Invoke(c) ?? c` |
| H2 | `OutpostHud.cs:715-724` and `SafeArea.cs:18-21` | A "reserved bottom space" setting so the CTA banner can sit under the bottom bar |
| H3 | `OutpostHud.cs:472-483` | Optional: a way to hide the Store and Cards buttons, or send them to the CTA |
| H4 | `OutpostController.Loop.cs:160` | Optional: a flag that suppresses the "While you were away" window |
| H5 | `Loc.cs:29,42-49,169-176` plus a new `Loc.Playable.cs` | A "Playable" section in the text dictionary |

## 1. Game configs and a playable-only balance

### How configs load
- **Loading the files:** `OutpostResources.LoadConfigs()` (`Runtime/Outpost/OutpostResources.cs:7-19`) reads the 7 files listed in `OutpostConfigSet.ResourcePaths` (`Core/Outpost/Config/OutpostConfigSet.cs:65-74`, all under `Resources/Outpost/*`). It then calls `Parse(...)` with 7 arguments (`:136-143`).
- **Called from:** `OutpostController.Init` (`OutpostController.cs:110-112`). It loads `Balance = OutpostResources.LoadSource(boot.BalanceJson)`, which reads `json-data.json` and verifies its checksum (`OutpostResources.cs:24-25`). Then it sets `Configs = LoadConfigs().WithCards(Balance)`.
- **Embedded copies:**
  - `OutpostConfigSet.Defaults.cs` is generated by `Tools/gen_outpost_config_defaults.py`. Its `FILES` list is at `:12-20`, it requires LF line endings (`:35-36`), and its output path is at `:11`.
  - `LoadDefault()` (`OutpostConfigSet.cs:104-106`) is used by the core logic and tests only, not by the running game.
  - The test `OutpostCoreSmokeTests.ConfigFiles_MatchEmbeddedDefaults_AndExactParsing` (`Tests/EditMode/Outpost/OutpostCoreSmokeTests.cs:238-253`) checks the embedded copies byte for byte against 4 of the files. It also checks `Balance.Version == "outpost-2.1-b4" == OutpostIds.BalanceVersion` (`OutpostIds.cs:14`).
- **Fingerprints (hashes):** computed in `RecomputeHashes` (`OutpostConfigSet.cs:175-184`). `CatalogHash` is the SHA-256 of Equipment, Rewards and CardRules only. Balance and Store are **not** part of `CatalogHash`. The hash is written into each save (`OutpostSaveService.cs:164`). On load, a different hash only sets the `CatalogChanged` flag (`:310`); it is not an error.
- **Each mine keeps a copy of its balance:** `StageProgressionService.CreateRun` copies `configs.Balance.Clone()` into `run.Balance` (`StageProgressionService.cs:56,71`). The simulation reads `Run.Balance` (`OutpostSimulation.cs:119,281`).
  - The only place that reads the current balance directly is `OfflineSimulator.OfflineCap` (`OfflineSimulator.cs:119`).
  - The save file's `BalanceVersion` field is informational only (`OutpostSaveService.cs:129`). Nothing at runtime compares it to `OutpostIds.BalanceVersion`.
  - Tests already confirm a profile switch takes effect from the next mine: `OutpostSaveTests.BalanceChange_DoesNotRebuildCurrentRun` and `OutpostBalanceRegressionTests.B3SaveMidMine_KeepsSnapshot_NextMineUsesB4_NoDuplicateRewards`.
- **Existing function for swapping balance:** `OutpostConfigSet.WithBalance(OutpostBalanceConfig)` (`OutpostConfigSet.cs:155-162`). It validates and recomputes hashes, and is already used by tests (`OutpostBalanceRegressionTests.cs:121`, `OutpostOfflineTests.cs:123`). `OutpostBalanceConfig.Clone()` is at `:118`, `Validate()` at `:136-181`.

### Cleanest playable overlay (main configs and saves untouched)
- **Hook H1** at `OutpostController.cs:112`, set by the playable library at startup before the scene loads. In the playable: `c => c.WithBalance(Overlay(c.Balance.Clone()))`.
  - Set `Version = "outpost-2.1-b4-playable"` so saves and logs are clearly marked.
  - Change only balance fields: Branch `BaseCost`/`Growth`, `HpBase`, `CoinBase`/`ValueGrowth`, `StartWorkers`, `TapDamageFactor`.
  - Do not change Equipment, Rewards or CardRules, so `CatalogHash` stays the same.
  - Keep `AreaFactorCap` and `AreaCapFromCells` consistent with each other (`:170-172`).
  - Speed parameters (`HitIntervalTicks`, `BaseMoveSpeed`) also drive animation. For example, the wind-up time is `min(0.3, 0.45·HitInterval)` (`OutpostBoardView.cs:432-433`). Prefer economy changes over speed changes.
- **Where to keep the overlay:** do **not** put it in any `Resources` folder. Every `Resources` folder ships in every build, including the main game. Use either C# multipliers, or a JSON string compiled into the playable library (the same approach as `Defaults.cs`). Do **not** add it to `gen_outpost_config_defaults.py` `FILES`, because that would change the core library.
- **Measuring the result without Unity:** `BalanceAudit.RunCampaign(repo, configs, model, seed)` (`Core/Outpost/Bot/BalanceAudit.cs:501`) takes any config set. Run it through `Tools/CoreTests/run.ps1 -Instance … -Filter …` (see `Docs/Rework/BALANCE_AUDIT.md:77-81`).
  - Current b4 baseline, measured from `Docs/Reports/balance-audit/after/campaign-*-seed1.json`:

    | Player model | Cumulative minutes, end of mines 1…6 | First delivery | First purchase |
    |---|---|---|---|
    | free | 5.2 / 9.4 / 14.8 / 19.3 / 25.4 / 31.1 | 10.5 s | 45 s |
    | active | 4.6 / 8.6 / 13.4 / 17.5 / 23.6 / 28.9 | 8.75 s | 23 s |

  - So the real first 30 minutes is about mines 1–6.
  - The guaranteed rewards in `stage_rewards.json` are a common pickaxe, hat, backpack and boots for mines 1–4, so the playable will fill all 4 equipment slots.
  - You could add a playable version of the pacing test `Campaign_FreePlayer_PacingWithinStageTargets` (`OutpostBalanceRegressionTests.cs:243-250`).
- **Caution on honesty:** `Docs/Marketing/research/meta.md:30` says "Don't promise speed the game doesn't deliver", and `:230-280` covers misleading-ad rulings. A faster playable balance than the real game conflicts with this. Keep the overlay moderate and document it.

## 2. Save slots and a no-save playable

- **Existing slots:**
  - `enum OutpostSaveSlot { Main, Debug }` (`OutpostSaveService.cs:11-15`).
  - Folders: `SlotDirectory` (`:109-110`) uses `slot==Main ? "main" : "debug"`. **Trap:** a new enum value would silently map to "debug". Paths are `:112-114`. Root folder is `CatOutpostV2` (`:77`).
  - Startup always loads Main: `LoadProfile(OutpostSaveSlot.Main)` at `OutpostController.cs:115`. `IsDebugProfile` is at `:30`. `SwitchProfile` (`:227-239`) only works in the editor or debug builds.
- **Override fields (existing):** `SaveDirectoryOverride`, `ClockOverride` and `FileSystemOverride` (`OutpostController.cs:19-21`) are used at `:85,113-114` and by every direct file access in `OutpostController.Save.cs:74,103,146,170,224`. PlayMode tests already set and clear them (`OutpostEvidenceTests.cs:33-53`, `AdCaptureTests.cs:56-87`).
- **Options for the playable**, all without touching main code:
  1. **No saving at all (recommended):** set `FileSystemOverride = new MemoryFileSystem()` before the scene loads. The `IFileSystem` interface is at `Core/Save/SaveService.cs:15-25`; copy the logic of the test helper `MemoryFileSystemA` (`Tests/EditMode/Outpost/OutpostTestHelpersA.cs:586+`) without its crash-simulation parts.
     - Effects: a fresh game on every launch; no IndexedDB writes during the 2-second autosaves (`Loop.cs:36-40`); the old-save import code (`Save.cs:95-206`) finds nothing.
     - In the playable web template, also set `autoSyncPersistentDataPath:false` (`index.html:55`).
  2. **Separate save that persists:** `SaveDirectoryOverride = persistentDataPath + "/playable"`. To reset on each launch, delete that folder before the scene loads.
     - Do **not** use `ResetProgress()` (`Save.cs:218-257`) for this. Each call copies `restart-<guid>` archives into IndexedDB (`:225-228`), which would pile up.
     - On WebGL, `persistentDataPath` is `/idbfs/<hash of the page URL path>` (Unity behaviour, verify), so a `/Cat-Miners/playable/` subfolder already gets saves separate from the main game.
  3. A real `Playable` enum slot would need changes at `OutpostSaveService.cs:110`, `OutpostController.cs:30,115`, `Save.cs:99,169`, plus new tests. Not worth it.
- **Background tab:** `PlayerSettings runInBackground: 0` (`ProjectSettings.asset:86`). Losing focus suspends the game; coming back runs the offline catch-up (`Loop.cs:193-216`). This happens even with in-memory saves.

## 3. Startup flow and how to select the playable mode

- **Startup order:**
  1. `GameBootstrap.Awake` (`Runtime/GameBootstrap.cs:29-47`): sets 60 fps. `LegacyMode` only applies in the editor or debug builds (`:37`). Otherwise it adds `OutpostController` and calls `Init(this)`.
  2. `OutpostController.Init` (`OutpostController.cs:81-118`): clock (`:85`), scene basics, camera rig, effects, sound, music, ambience, board (`Board.Cue += OnBoardCue` at `:101`), `OutpostHud.Create` (`:103`), input, `new OutpostTutorial` (`:107`), source data (`:110`), configs (`:112`), save folder and service (`:113-114`), then `LoadProfile(Main)` (`:115`).
  3. `LoadProfile` (`:176-225`): either loads, migrates and runs `BeginOffline`, or starts a new game (`ArchiveLegacySaves`, `StageProgressionService.NewGame`, old-settings and old-cards import, `StoreService.MigrateProfile`, `Commit`, then `Playing`).
- **The scene is regenerated:** `ProjectSetup.RunBatch` uses `Run(force:true)` (`Editor/ProjectSetup.cs:56-60`). It recreates `CoreGame.unity` (`:99,213-224`) and resets `EditorBuildSettings.scenes` to CoreGame only (`:101`). The CI path always runs Setup before BuildWeb (`Tools/unity.ps1:265-271`). Any flag stored on a scene component would be wiped in CI.
- **Selecting the mode:**

| Method | Pros here | Cons here |
|---|---|---|
| **Build flag** `CATMINERS_PLAYABLE` via `BuildPlayerOptions.extraScriptingDefines` in a new `BuildWeb.Playable()`, plus a flag-gated code library (same pattern as DevTools) | Playable code is physically absent from the main build. ProjectSettings untouched (`scriptingDefineSymbols: {}` at `ProjectSettings.asset:829`; the CI copy is overwritten from the project anyway, `unity.ps1:73-82`). Attaches like `OutpostDevPanel.cs:20`. | Editor work needs the flag. A Unity 6 Build Profile can carry flags (`Assets/Settings/Build Profiles/Web.asset` exists with `m_HasScriptingDefines: 0`). Playable tests need their own test library gated on `UNITY_INCLUDE_TESTS` and `CATMINERS_PLAYABLE`. **Risk:** if the flag is active in the editor, its startup code also runs in the main PlayMode tests. Guard it (for example, require an explicit editor toggle) and clear every new static field. |
| ScriptableObject or JSON flag in `Resources` | Easy to toggle in the editor | Ships in the main build. The build script must flip it and restore it; a crashed build leaves the main game flagged (and the file syncs to the PC). Playable code ships in the main build. |
| URL query (`Application.absoluteURL`, for example `?mode=playable`) | One build serves both | Anyone can turn the main site into the playable. No size savings. Empty in the editor. Ad networks often serve single-file pages or blob URLs where the query is lost. Best used only for parameters inside the playable build (`?store=`, `?net=`). |

## 4. Interface (HUD) extension points, built only from PixelUi

### Layout constants and where the margins are computed
(`Runtime/Outpost/UI/OutpostHud.cs`; `Px = 4` canvas units, `PixelArt.cs:42`; reference size 1080×1920, width/height match 0.5, `:30`)

| Item | Location | Value |
|---|---|---|

| Bottom area | `:38-45` | `BottomUnits = 8+208+8+176 = 400` (bar plus the strip above it) |

| Toast position | `:55` | `ToastTop = 248`, width 0.07…0.93 |
| Plaque | `:46`, `:356` | 20% width, top-left |

- Top bar is built in `BuildTopBar` (`:353-419`), bottom bar in `BuildBottom` (`:465-515`). The bottom button order (Store, Cards, Base, Equipment, To base) is at `:472-483`.
- Everything sits under the `SafeArea` object (`:313-349`). Child order is the drawing order.
- **Margin calculation:** `UpdateInsets` (`:715-724`) divides by `m_Safe.rect.height`. `PushInsets` (`:737-745`) passes the values to `CameraRig.SetUiInsets` (`CameraRig.cs:110-116`; camera fit at `:211-228`, `SafeFractions` at `:250-259`; the camera uses `Screen.safeArea`). Field-tap bounds come from `FieldBandPixels` (`:238-244`), used by `OutpostInput.cs:34-38` and `OutpostTutorial.cs:390`. Reserved space for tutorial hints: `Hint.SetReserved(BottomUnits, TopUnits)` (`:326`). The info panel is anchored at `BottomUnits+Margin` (`OutpostHud.Info.cs:31-32`).
- **Why the CTA banner needs hook H2:** `SafeArea.Update` (`SafeArea.cs:12-22`) resets the safe-area offsets to zero whenever the screen changes, for example on a browser resize. So:
  - `SafeArea` needs a reserved-bottom value that it keeps applying.
  - `UpdateInsets` must compute `bottom = (BottomUnits + reserve)/(units + reserve)` and `top = TopUnits/(units + reserve)`, so the fractions stay relative to the **full** `Screen.safeArea` that `CameraRig` uses. The fallback at `:726-734` needs the same reserve.
  - With that in place, all windows, the bottom bar, toasts and hints move above the banner automatically.
  - Draw the banner itself on a separate overlay canvas: `sortingOrder 30001+` (the HUD uses 30000, `:269`), the same `CanvasScaler` settings, and its own `SafeArea`, so it also stays above the transition fade (`:848-863`).
- **Other HUD hooks:**
  - Back button: `WindowEntry` (`:96-100`) and `Opened`/`Closed` (`:750-758`) are private. `HandleBack` (`:790-815`) and the `PollBackButton` field (`:183`) are public. For overlay popups, set `Hud.PollBackButton=false`; the overlay closes its own popup or else calls `Hud.HandleBack()`.
  - Public functions: `Toast(text, sec)` (`:564`); `Modal(title, body, icon, buttons)` with a queue, integrated with the window stack and Back (`OutpostHud.Results.cs:382-435`); `CloseAllWindows` (`:828`); `AnyWindowOpen`/`BlockingWindowOpen` (`:189-206`); `OnWindowOpened`/`InsetsChanged` events (`:212,215`); `FlyCoins` (`:635`); `Hint` (`:174`); state flags `ResultsOpen`/`ChestRewardOpen`/`StoreOpen` (`Results.cs:55-60`, `Store.cs:63-72`).
- **Building blocks for the new UI:**
  - `PixelUi.Panel/Icon/Text/Button/IconButton/Badge/Bar/IconText/Window` (`PixelUi.cs:262,276,319,382,428,459,506,523,593`). `PixelPop` gives the pop-in animation (`PixelPop.cs:10-20`).
  - `OutpostDialog.Create(safe, name, onClose)` is public (`OutpostDialog.cs:64`). Use it for "QUEST COMPLETE! Tap to claim" and for the end card (its shade can be dimmed like `Results.cs:95`).
  - Available atlas icons: `icon_star` (use for ★★★★★; Pixeloid has no ★ glyph and would fall back to LiberationSans, `UiKit.cs:84-98`), `icon_cat_big`, `icon_cat`, `icon_chest_big`, `icon_check`, `icon_coin`, `icon_pickaxe`, `ui_portrait_frame`, `ui_btn_gold/green`, `ui_toast`, `ui_pill`.
  - There is **no** app-icon or logo sprite. Either use `icon_cat_big` in `ui_portrait_frame`, or add a sprite through the existing atlas pipeline.
- **Quest tracker placement:** the top-left area under the plaque (y −136…) collides with the tutorial skip button (`:416`) while the tutorial runs, and the centred toast starts at −248. Hide the skip button, which happens when the tutorial is dismissed, or place the tracker at y below −248.
- **Taps on overlay UI:** they are blocked from reaching the play field automatically. `OutpostInput.cs:71` uses `IsPointerOverGameObject(id)`. `FieldEnabled` (`:33`) only looks at HUD windows.

## 6. Mine transitions and features a 30-minute playable may hide

- **Next mine:**
  - `ContinueToNextMine` (`OutpostController.Commands.cs:126-136`) prepares the transition, saves, then runs `ShowTransition` (`:138-163`; ends with `BeginOffline(showSummary:false)` at `:162`). `CanContinue` is at `OutpostController.cs:43-44`.
  - The Results window opens on its own (`OutpostHud.Results.cs:150-157`; `ShowResults` at `:172`; Next button at `:237-249`). The strip "Next mine" button is at `OutpostHud.cs:1170-1192`.
  - **Auto-continue from the overlay is safe:** when `CanContinue && !Hud.ChestRewardOpen`, wait N seconds and call `ContinueToNextMine()`. The transition closes all windows (`OutpostHud.cs:861`) and the new mine hides the old results (`:955-961`). The test `OutpostRuntimeTests.NormalTransition_DoesNotOpenOfflineSummary` covers this path.
- **Offline catch-up:**
  - Window logic: `Loop.cs:122-188`. The summary appears if at least 5 s passed (`:160`). Focus and pause handling: `:193-217`.
  - On the web, switching tabs leads to the catch-up progress window and then "While you were away" (`Results.cs:138-143,295-303`), which includes an ad-reward "Double income" button (`Commands.cs:97-110`; `TestPurchases: true` in `store_catalog.json:3`).
  - Calling `DismissOffline()` from the overlay leaves the window visible for at least one frame plus its open sound, so hook H4 is cleaner.
- **Store:** `ShowStore` (`OutpostHud.Store.cs:176`). Time skips (`Commands.cs:70-91`) and test purchases for real-money gem packs (`store_catalog.json:15-20`).
- **Settings:** reset progress, tutorial toggle and play time (`OutpostHud.Settings.cs:36-60`).
- **Cards:** button at `OutpostHud.cs:476-477`.
- **Hiding buttons:** `RefreshBottom` only toggles interactivity, not visibility (`:1061-1074`). So `Hud.transform.Find("SafeArea/Bottom/BottomBar/Store").SetActive(false)` works without code changes, but it is fragile and leaves gaps, because the Base button uses fixed side offsets (`:487-488`). Hook H3 is the clean version.
- **Already excluded from release builds:** DevTools (`DEVELOPMENT_BUILD` flag) and LegacyMode (`GameBootstrap.cs:37`).

## 8. CTA store link and ad-network detection

- **Existing code:** none. There is no `OpenURL`, `absoluteURL`, `.jslib` or `DllImport("__Internal")` anywhere in `Assets`. The only store-related value is the bundle id `com.catminers.prototype` (`ProjectSetup.cs:36`), and there is no store listing URL. Make the URL a template variable (`{{{ STORE_URL }}}` via `PlayerSettings.SetTemplateCustomValue`) or a `?store=` query parameter, with the main web game as fallback.
- **`Application.OpenURL` on WebGL:** it opens a new tab, but the C# code runs a frame after the actual tap, so iOS Safari may block it as a popup. A robust pattern is a `.jslib` function that arms a one-time `pointerup`/`touchend` listener on the canvas and calls `window.open` inside that real gesture.
- **`.jslib` sketch:** put it in `Assets/Game/Scripts/Playable/Plugins/CatMinersPlayable.jslib`. Plugin define constraints (verify) can limit it to `CATMINERS_PLAYABLE`. On the C# side, use `[DllImport("__Internal")]` under `#if UNITY_WEBGL && !UNITY_EDITOR`.
  - `CM_Network()`: return `typeof mraid` ("mraid": AppLovin, Unity, Vungle, Mintegral), `FbPlayableAd` (Meta), `dapi` (ironSource), `ExitApi` (Google), `playableSDK` (TikTok/Pangle), otherwise "web". Allocate the string with `lengthBytesUTF8`/`_malloc`/`stringToUTF8`.
  - `CM_OpenStore(urlPtr)`: call `mraid.open(url)`, `FbPlayableAd.onCTAClick()`, `dapi.openStoreUrl()`, `ExitApi.exit()`, or `window.open(UTF8ToString(urlPtr),'_blank')`.
  - With MRAID, wait for the `ready` event before use. Verify each network's current spec.
- **In-Unity banner vs HTML banner:** an HTML CTA outside the canvas avoids popup blocking. But it is not built from PixelUi, and clicking outside the canvas can trigger the focus/suspend path (`Loop.cs:193-216`, `runInBackground:0`).
