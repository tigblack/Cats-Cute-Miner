# candidates
## FormulaType 0 (все поля) [medium]
- formula: f(x) = B + M·x + G·x²
- arg: x = уровень сущности, считается с 1: уровень карты, генератора, камня. Для Reinforcements.Level x = число наймов n, считается с 0. Для CheckPoint и констант x не влияет.
- round: Внутри формулы нет. Уровень найма = 1 + floor(f). Валюта округляется по отдельному правилу, рабочее предложение — до целого.
- for: У всех FT0 вне карт G = 0, там форма линейная, и B + M·L при B = 0 требует L ≥ 1 (выход генератора). Выход кузницы на L1 = 3/2 с = 1.5 г/с = NoGeneratorsCurrencyRate. Для карт квадратичная форма с x = L даёт на максимальном уровне редкости круглые значения: ca031 0.601, ca033 0.4995, ca050 1.001, ca054 0.798, ca052 0.252, ca051 0.15, ca053 1.0 (4.5−0.5·7), ca062 0.30. Суммарная ошибка «круглости» 0.06; у вариантов x = L−1, L(L−1)/2 и L(L+1)/2 — 0.17…0.37 (ft0_cards.py). При x = L−1 у большинства карт эффект на L1 равен 0.
- against: Это подгонка по признаку «круглого» итога. ca026 (48.6) и ca027 (10.8) на максимуме не круглые. Арифметическая прогрессия B + M·L + G·L(L−1)/2 тоже даёт часть круглых значений (0.50, 0.75, 1.0).

## FormulaType 0 / Reinforcements.Level (уровень покупаемого кота) [low]
- formula: level = 1 + floor(0.4 + 0.125·n); уровень бесплатного кота из пушки = max(1, level − 1)
- arg: n — число наймов за золото в текущей зоне, считается с 0, сбрасывается при смене зоны. Вариант: n+1.
- round: floor плюс 1, то же самое, что ceil. Дробная часть — шкала на кнопке найма.
- for: Без +1 при n = 0 уровень был бы 0. Вики: шкала заполняется покупками, затем уровень растёт на 1 (0.125 = 1/8, то есть +1 уровень за каждые 8 наймов). Вики: «Cannon level = purchase level − 1» соответствует SpawnLevelOffset −1.
- against: Смещение 0.4 и +1 публично не подтверждены. Неизвестно, учитываются ли бесплатные коты и коты из доставок. Неизвестно, влияет ли на уровень Golden Cannon (SMT4) или ворота. При уровне найма 1 пушка дала бы уровень 0, поэтому нужен clamp.

## FormulaType 1 (общая форма) [medium]
- formula: f(x) = B + M·G^x
- arg: У карт x = уровень карты с 1. У урона, найма и динамита — см. отдельные записи.
- round: нет
- for: Везде, кроме Spells, B = 0. Совпадает с публичными ×2.1 за уровень кота и ×4 за найм. Для карт x = L нужен, чтобы легендарные карты действовали уже на L1: Golden Cart ca034 даёт ×3 при x = L и ×1 (без эффекта) при x = L−1. FT0-карты того же поля надёжнее показывают x = L.
- against: Форму M·G^(x−1) нельзя исключить: тогда Multiplier — значение на уровне 1, а manager-карта на L1 только автоматизирует шахту, что тоже правдоподобно.

## FormulaType 1 / Miners.Damage (урон кота) [low]
- formula: рабочий: dmg(L) = 2.1^L (L1 = 2.1). Альтернатива: 2.1^(L−1) (L1 = 1)
- arg: x = уровень кота. Рабочий выбор x = L (как у карт); альтернатива x = L−1.
- round: Нет. HP — дробный остаток.
- for: Единое соглашение «x = уровень» с картами и выходом генераторов. Оба варианта проходят zone1. В sim.py zone1 бот проходит за 39 с при x = L и за 77 с при x = L−1.
- against: Ничто в данных не фиксирует базу; ТЗ прямо требует не выдавать выбор за оригинал. Если читать Multiplier = 1 как «урон L1», выходит x = L−1. Разница — ровно один уровень кота (×2.1) во всех временах.

## FormulaType 1 / Reinforcements.Cost (цена найма) [medium]
- formula: cost(n) = 2·4^n / 10^k, где k — число открытых ворот (код 2: ModifierBase 10)
- arg: n = число уже сделанных наймов, считается с 0: первая цена 2, затем 8, 32, 128… Альтернатива n+1: первая цена 8.
- round: Не определено. Рабочее правило: показ округлять, списывать точное значение double.
- for: Вики: ×4 за покупку в основной шахте, ворота дают скидку. При стартовых 25 золота оба варианта сразу доступны: 2 или 8.
- against: Первая цена публично не названа. Скидку ворот ×10 для основной шахты дал только вывод по аналогии с ивентами (средняя уверенность).

## FormulaType 1 / Spells.Effect (динамит) [medium]
- formula: dmg = 750 + 300·2.1^x, x по тому же соглашению, что урон кота
- arg: x = уровень динамита (вики: уровень сильнейшего кота); база та же, что у Miners.Damage
- round: нет
- for: 300 с × урон кота того же уровня совпадает с вики: «5 минут работы кота того же уровня, ×2.1 за уровень».
- against: Смысл B = 750 неясен: на низких уровнях это добавка 5–12 минут. Возможна и иная роль Base.

## FormulaType 2 / UpgradeCost (кузница и шахты) [low]
- formula: cost(L→L+1) = B·G^(L−1); M = 0 во всех 21 записи, поэтому член с M не влияет
- arg: x = число уже купленных улучшений = уровень − 1. Первая цена = Base: кузница 72, amethyst 512, citrine 4096. Альтернатива x = L: 103 и 747.5.
- round: Не задано. Списывать точное double, показ округлять. Цена пакета «До порога» = сумма шагов.
- for: Base подобраны как «круглые» числа, похожие на цену первой покупки: 512 = 8³, 4096 = 8⁴, 32768 = 8⁵, 9765625 = 5¹⁰, 6103515625 = 5¹⁴, 470184984576 = 6¹⁵. Это естественно для «цены первого улучшения». Принцип «x = число покупок» совпадает с выбранным для найма.
- against: Прямого подтверждения нет. При x = L все цены выше в G раз (1.43–1.90).

## FormulaType 2 / BalanceProperties.DeliveryDelaySec [low]
- formula: a) 22·1.02^x + 1·x (рабочий); b) (22 + x)·1.02^x; c) 22·x^1·1.02^x (M — показатель полинома; при M = 0 у цен улучшений x^0 = 1)
- arg: x = число полученных доставок за окно 3600 с (DeliveryClaimCountResetSec); первая доставка по DeliveryStartupDelaySec = 20. Затем ±10% Variance.
- round: нет
- for: Все три варианта совпадают с UpgradeCost при M = 0. a) и b): 22 → 37–39 с после 10 доставок, около 70–94 с после 30, примерно 60–70 доставок в час. c): 22, 46, 70 … 268 с после 10, примерно 15–18 доставок в час. Это ближе к разумной доле дохода от доставок.
- against: Данных для выбора нет; оценка частоты различается примерно в 4 раза. Сам аргумент x тоже не подтверждён.

## FormulaType 3 (общая форма) [low]
- formula: A (рабочий): f = roundTo(B + M·(G·x)^P, |R|). B (альтернатива): f = roundTo(B + M·(1 + G·x)^P, |R|). Экспоненциальные варианты отброшены: камень L60 давал бы годы дохода.
- arg: A: x — уровень камня с 1 или ранг зоны; при x = 1/G значение равно B + M (камень L5 = 645 с; доставка на ранге 10 = 5/10/15/25/125 мин). B: значение B + M достигается при x = 0, значит у камней x = L−1.
- round: До ближайшего кратного |Round|; при Round = 0 округления нет. Знак Round, вероятно, задаёт направление, но в текущих данных отрицательный Round есть только при M = 0 и целом B, поэтому ни на что не влияет.
- for: A: Base имеет смысл при малых x. Пример — BattlePass Legacy (Base −4.5): при A значение примерно 0 на рангах 1–2 и положительно с ActivationRank 7. Мягкие доставки при A дают 6–35 эликсира (обычные) и 165–295 (рекламные) на рангах 4–7, это соразмерно сундукам (Wooden 45–55). B: у камней 10 + 635 = 645 = 43·15, у Core-доставок M кратно 60, все параметры независимы.
- against: A: M и G частично избыточны (M·G^P). B: у мягких доставок Base 0.7/2.5 ничтожен рядом с M 200/600, а при x = 0 они дают 200–600 эликсира — больше деревянного сундука. При больших x формы сходятся, расходятся только на старте: камень L1 даёт 105 с (A) против 645 с (B).

## FormulaType 3 / Rocks.CoreCurrencySeconds и GetRewardIncomeRate [low]
- formula: gold = FT3_A(10, 635, 0.2, 1.15, 15; x = уровень камня) × rate. rate = доход/с кузницы + автоматизированных шахт с учётом порогов и бонусов, но не меньше NoGeneratorsCurrencyRate = 1.5
- arg: x = уровень камня из токена r, считается с 1
- round: Секунды — до кратного 15. Золото не округляется.
- for: Ненулевые параметры только у камней, дающих Core (rockbasic и onboarding), а их RewardCycle содержит Core с Quantity 0. 1.5 = доход кузницы на L1. Вики: «зелья времени дают золото, которое произвели бы кузница и шахты», то есть понятие «секунды дохода» в игре есть.
- against: Неизвестно, входят ли в rate ручные шахты и временные бусты. Обратная связь «награда = секунды × rate» доминирует в экономике (sim.py: rockgold на порядки больше прочих источников), так что любая ошибка здесь сильно меняет темп.

## FormulaType 3 / Deliveries.Quantity [low]
- formula: Core: секунды = FT3_A(0, M, 0.1, 2, 60; x = ранг), затем × rate. Soft: эликсир = FT3_A(...; x = ранг). Коты: уровень = уровень найма + QuantityBase, не ниже 1. Динамит — отдельный resolver.
- arg: x = ранг, то есть номер зоны (у Deliveries есть RankUnlock; DeliveryStartRank = 4)
- round: |Round|: 60 с, 5 или 1 эликсира, 1 уровень

- against: Аргумент «ранг» не подтверждён. При B уже на ранге 4 обычная доставка даёт 10 минут, а рекламная — 4 часа. Смещение кота может отсчитываться от пушки, а не от найма; вики противоречит себе.

## FT1 / Cards: manager SMT9 и Golden Cart SMT10 [low]

- round: нет
- for: Вики: «Automate and increase the profit»; CheckPoint код 10 = ×2 к доходу. Совпадение по MU и редкости подтверждает соответствие ID и названия.
- against: Множитель за уровень публично не подтверждён. ТЗ запрещает назначать эффект SMT9 только по догадке, поэтому в рабочем профиле это отдельно помеченный переключатель.

# recommendation
1) Как сформулировать в ТЗ. Исходного кода нет, поэтому раздел 4.2 должен прямо разрешать и требовать отдельный экономический профиль WorkingProfile (PrototypeCompatibility v0). Профиль хранится данными (ScriptableObject или JSON рядом с исходным), его ID и hash пишутся в сохранение. Каждое поле *FormulaType вычисляется только через FormulaEvaluator.Evaluate(fieldKey, context) по записи профиля. Запись содержит:
- форму функции;
- источник аргумента: UnitLevel, CardLevel, GeneratorLevel, RockLevel, ZoneRank, HireCount, UpgradesBought, ClaimCount, ThresholdIndex;
- смещение индекса;
- режим округления и clamp;
- статус: Verified-by-data / Public-reference / Assumption;
- ссылку на обоснование.
Любой переключатель меняется в одном месте без правки JSON и кода систем. В отчёте и в отладочной цепочке «база → формула и аргумент → модификаторы → результат» показывается ID профиля. Ни одна запись не называется оригинальным алгоритмом.

2) Что закрепить в профиле как контракт (уверенность от высокой до средней):
- HP = table[level−1].
- Пороги GeneratorObjectives — интервалы от уровня 1 (первый на 10), множители перемножаются, за конец массива не выходить. Подтверждено вики в 50 и 24 точках.
- Рост ×2.1 за уровень кота и динамита, ×4 за наём (вики).
- CardUpgradeCosts[0] = переход 1→2 (вики).
- FT0: B + M·x + G·x², где x — уровень с 1 для карт, генераторов и камней. Выход генератора = M·L × пороги; задержки — константы.
- FT1: B + M·G^x, для карт x = уровень карты с 1.
- FT2 для цен улучшения: B·G^x, член с M при M = 0 не влияет.
- CheckPoint: значения FT0-констант накапливаются за каждые открытые ворота. Коды 10/2/7/1 = доход ×2, скидка найма ×10, таймер −60 с, лимит +1 — вывод средней уверенности, помечается как Public-reference.
- Округление FT3 — до кратного |Round|.

3) Рабочие допущения (низкая уверенность). Каждое — отдельный переключатель с указанной альтернативой:
- (a) урон и динамит: 2.1^L (рабочий) или 2.1^(L−1);
- (b) аргумент цены найма: n с 0 (первая цена 2) или n+1;
- (c) уровень найма = 1 + floor(0.4 + 0.125n); пушка = max(1, уровень − 1);
- (d) аргумент UpgradeCost: L−1 (первая цена = Base) или L;
- (e) форма FT3: A, то есть B + M·(G·x)^P (рабочий), или B, то есть B + M·(1 + G·x)^P; для камней x = уровень камня, для доставок x = ранг;
- (f) GetRewardIncomeRate = кузница + автоматизированные шахты, не меньше NoGeneratorsCurrencyRate; ручные буферы не входят;
- (g) форма FT2 для DeliveryDelaySec: a, b или c; x = число доставок за 3600 с;
- (h) x для эликсира за порог GeneratorObjectives: номер порога или уровень;
- (i) эффект manager-карт SMT9 и Golden Cart SMT10 = множитель M·G^L. По ТЗ это допустимо только как помеченное допущение. Если оно выключено, карта только автоматизирует шахту.
