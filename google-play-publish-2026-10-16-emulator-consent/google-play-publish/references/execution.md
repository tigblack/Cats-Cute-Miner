# Выполнение без повторной работы

Это правила ускоренного процесса для всех режимов. Они уточняют применимость подробных справок: SDK/платежи/подпись/Console evidence сохраняются; маркетинг выполняется, когда заказан. Режим не является новым разрешением на внешнюю запись.

## Scope и маршрут

`setup` завершает нужные интеграции; `release` — Android/internal и оформление; `update` — следующий билд существующей игры; `marketing` — три видео и short/long; `full` — release+marketing. Явное поручение имеет приоритет над default. Для первого release недостающий setup входит в работу. Сохрани режим и запрошенные deliverables в `workflow` существующего profile.json; не создавай отдельную копию профиля на режим.

Не подменяй полный комплект урезанным. Если заказан full, производи все материалы, используя параллельные направления. После release можно показать достигнутый промежуточный результат, оставив marketing незавершённым. Update не регистрирует повторно сервисы и не переснимает подходящие материалы. Если интеграция не завершена, исправь конкретный пробел, а не запускай заново весь setup.

## Параллельная работа

Независимые направления: SDK/код; оформление/тексты; видео/playable. Выдай каждому точные пути и результаты. Не редактируй одни файлы/сцену двумя исполнителями; тестовые saves изолированы от прогресса владельца. Если инструменты дают только одного пишущего агента, другие занимаются чтением/проверкой/подготовкой требований. Несколько Editor-процессов на одном проекте запрещены. Общие изменения интегрируй до финальной сборки.

Внешние чтения разных сервисов могут идти параллельно. Сначала прочитай account/catalog и существующие записи; создания выполняются последовательно относительно их зависимостей и конфликтующих ресурсов. Console/browser worker имеет одного владельца; не запускай параллельные browser-команды и не открывай новую вкладку при каждом retry.

Каждый запуск/перезапуск Android-эмулятора требует отдельного вопроса и явного согласия на этот запуск ([emulator.md](emulator.md)); QA, retry и новая версия не дают автоматического разрешения. Явное поручение опубликовать без runtime-прогона выполняй без эмулятора, сохранив непроверенные статусы.

## Reuse доказательств

Сначала сравни фактические изменения, а не все файлы. Для повторяемого gate сохраняй входы и их fingerprint, предыдущее evidence_ref, время и причину reuse/invalidation. Fingerprint включает применимые исходники, версии и resolved dependencies, config, package, среду и ABI; для runtime — также consent/подписку/lifecycle, для денег — ledger/catalog/reward mapping.

| Что изменилось | Что повторить |
| --- | --- |
| Только versionName/versionCode | Финальная сборка/manifest/signature, установку той же новой версии и общий smoke; не регистрировать сервисы заново. |
| SDK/bridge/consent/lifecycle/config/ABI | Затронутые compile/init/use/delivery/device gates. Не считать прежний runtime PASS актуальным без сравнения входов. |
| Цена/SKU/reward/ledger/purchase flow | Нужное согласование каталога, readback metadata и денежные сценарии, включая однократность/отказы/recovery. |
| Текст/иконка/скриншоты/локаль | Изменённые assets, launcher resources при изменении иконки, один полный save/reload/readback текущей listing. |
| Playable/video | Проверку новых финальных байтов и затронутого поведения. Другие неизменные варианты сохраняют свой SHA и evidence. |
| Другая учётка/package/environment | Соответствующие внешние bindings/права/доставка; старые IDs и credentials не переносить. |

Одинаковые `null`/unknown — не совпадение. Изменившийся scope/config или неподтверждённый fingerprint инвалидирует gate. Предыдущая запись остаётся исторической; для новой сборки явно раздели текущий smoke и унаследованную проверку неизменного компонента. На неизменном AAB при переносе трека не повторяй локальную сборку и device тесты; новый трек/статус всё равно перечитай.

## Сборка и Console

Используй существующие build/test/export scripts. Сначала необходимые compile checks изменённых частей, затем один финальный signed release AAB после всех изменений кода/иконок. Billing bootstrap нужен лишь при фактическом prerequisite Console. После новой правки/ошибки повтори затронутую сборку/проверку; не собирай отдельно на каждый SDK или второй трек.

Одним обходом наблюдаемой формы собери inventory. Подготовь все значения и assets, заполни форму, дождись обработки, сохрани, один раз заново открой и прочитай всё применимое, включая Phone/7-inch/10-inch. Используй групповые API/DOM readbacks и существующий verify_listing.py. Не снимай новый полный отчёт после каждого введённого поля. Save/readback после финальной правки всё равно обязателен. Не обходи неизвестное/пустое обязательное поле или подтверждение размеров metadata.

Кадры снимаются из игры на нужном языке. Переиспользуй утверждённую композицию/систему подписей и существующий экспорт; генератор нужен для нового дизайна и самостоятельных акцентов. Не генерируй уже подходящие assets и не перерисовывай HUD ради перевода, если можно снять реальную локализованную игру. Просмотр новых/изменённых изображений сохраняется.

## Таймауты и ожидания

Действия в Play Console идут через agentb ([browser.md](browser.md)): действие ограничено 15 с, навигация 60 с, длинные процессы Google проверяются короткими повторными `text`, а не одним ожиданием. Двенадцатиминутные ожидания ниже относятся только к запасному серверному воркеру.

Bundled MCP client различает короткие чтения, обычные записи и долгие browser-worker операции; точные defaults/override — [superleo.md](superleo.md). Initialization ограничен отдельно. Длительный CLI запускай с отдачей управления, продолжая независимую работу; не оставляй пользователя без содержательного обновления больше минуты.

После timeout write считай исход неизвестным. Сохрани requestId/job ID/package/version/hash и ищи результат; не повторяй создание/публикацию потому, что клиент не дождался ответа. На выбранном маршруте допускается одна восстановительная попытка после новой диагностической информации и readback. Auth/permission/provisioning failure без изменения условий — ожидание доступа/службы, а не бесконечный перебор API/селекторов. Новые доступы/новая информация позволяют возобновить шаг.

Если API возвращает job ID, наблюдай эту же задачу с умеренным polling; не создавай новую. Не выводи из факта timeout, что server job отменён. На зависшем browser worker сначала проверь здоровье/текущую задачу и страницу; второй процесс не запускай, пока первый не завершён/безопасно остановлен.

## Отчётность и тайминги

Один profile.json, status.md и ссылки на машинные receipts. Шаблоны/manifest формируй из существующей схемы и наблюдаемого scope; не переписывай вручную одинаковые описания в каждом файле. Не придумывай receipts и не ставь успешные статусы из шаблона.

В `workflow.timing_log_ref` сохрани путь к фактическим start/end записям по этапам: discovery, integration, build, Console, assets/marketing, device QA, waiting. Тайминг фиксирует наблюдаемое elapsed, а не обещанную оценку. В итоге отдели активную работу от ожидания доступа/внешнего processing. Проверка общего workflow не обосновывает прежние восемь часов без их лога.

Не добавляй новый scheduler/кэш-сервер/генератор отчётов для одного запуска. Используй профиль, CLI и штатные инструменты. Секреты и результаты управления в private файлах; отчёт показывает только нужные IDs и статусы. [state.md](state.md), [handoff.md](handoff.md).
