# Контракты SDK и связи между сервисами

Используй при интеграции/релизе и при запросе аудита SDK. Проходи применимые сервисы целиком, даже если жалоба только на покупки или рекламу. При update повторяй изменённые контракты и smoke новой установки; повторная регистрация неизменных приложений/каталога не нужна. Это карта проверок, а не разрешение на публикацию, смену цен или переустройство рабочей рекламы.

## Фактическая карта проекта

Для каждого сервиса запиши: wrapper и **resolved native version**, package/app ID и окружение, файл/метод bootstrap, источник consent, lifecycle, реальные callers, auto/manual сбор, retry/dedup, доказательство получения. Сверь API с установленным пакетом и актуальной официальной документацией; номер Unity/UPM-плагина не равен native версии. Инвентарь файлов и флаги READY не проверяют эти контракты. Toolchain caches исключай из выводов о текущей реализации.

Не связывай независимые функции общим «все SDK готовы»: отказ аналитики не блокирует Billing/награду, отсутствие рекламы не блокирует магазин. Зависимости consent сохраняются: если MAX владеет native CMP, его завершение служит входом в разрешённую инициализацию аналитики; timeout MAX не является завершением CMP. Игра может продолжиться, но измерение не объявляется готовым. При другой архитектуре CMP опиши её фактический callback.

## Проверка каждого SDK

| Сервис | Что должен делать | Что проверять в коде/конфигурации | Доказательство runtime |
|---|---|---|---|
| AppMetrica | Основная продуктовая аналитика с JSON-контекстом; выбранные ad/IAP revenue | Собственная app/API key; один activation, lifecycle; consent до сбора и после отзыва/restart; реальные игровые события и сохранённая форма payload. Auto IAP и auto ad revenue проверять раздельно в resolved modules и subscriptions. `RevenueAutoTrackingEnabled=false` не отключает отдельный ad-revenue модуль. | Старт, прогресс и экономика получены этой app с нужными полями; отдельно денежный отчёт. При недоступности сервиса SDK/events сохраняются, delivery waiting по правилам скилла. |
| Adjust | Attribution/install/session, зеркало игровых событий, специализированный ILRD и purchase revenue | Own app/package/environment, event tokens и caller coverage; lifecycle по платформе; install referrer/дополнительные плагины только по выбранному измерению. Отказ/отзыв consent и third-party sharing применяются к SDK; dashboard sharing проверяется отдельно. Init и enqueue не равны attribution/delivery. | Session/install, representative custom events, ILRD и новая покупка в правильной app/environment. Отдельный readback партнёров и event mapping. |
| Meta App Events | Activation, выбранные игровые события и покупки | App ID/client token, package/activity, hashes фактического Play App Signing сертификата; отключённые pre-init providers/flags до разрешения. Проверь реальные init/ActivateApp и event callers, а не только allowlist имён. После ActivateApp проверь зарегистрированные lifecycle callbacks/очередь: отключение ручных LogEvent и advertiser ID само по себе не доказывает прекращение всех автоматических событий при отзыве. | Activation и каждое выбранное событие доходят в app. Покупка соответствует выбранному единственному денежному маршруту. Audience Network adapter и Adjust→Meta feed не доказывают работу App Events SDK. |
| MAX | Mediation, загрузка/показ включённых форматов, reward и ILRD callbacks | Init callback/privacy result, собственные units; adapters+native dependencies+runtime network settings. MAX управляет mediated SDK initialization: второй ручной init сети создаёт конфликт. CMP должен содержать участвующие сети; Terms URL не заменяет опубликованную CMP message. Проверь geography, отказ, изменение consent, resume и retry. UNKNOWN geography не приравнивается автоматически к OTHER; `canRequestAds` не является boolean «согласен». Один и тот же предикат должен согласованно управлять load/show/banner/retry. | По каждому включённому формату load→show→close/error; rewarded→один durable grant; revenue→правильный получатель. Каждый сетевой adapter/placement проверяется отдельно от успешного показа одной сети. |
| Billing + Multicast | Store checkout, server validation, durable grant и recovery | [Checkout](server-iap.md#google-play-checkout-до-сборки), идентичность game/player/order/SKU; оригинальный receipt; точная серверная награда; atomic save до claim/confirmation; current ownership; отсутствие дубля при restart/restore. Аналитика не разрешает выдачу и не задерживает store confirmation. | Реальная Play license-test транзакция→payment/reward→сохранённая награда→consume/ack→restart/restore без дубля. Admin SKU ACTIVE и negative receipt не заменяют этот сценарий. |

Для AppMetrica/Adjust зеркала проверь не только наличие имени: producer payload → фильтр/агрегатор → SDK payload. Нельзя молча потерять поле контекста в общей allowlist, целое событие из-за отсутствующего токена или при несовпадении имён. Высокочастотную экономику агрегируй без per-frame JNI; test clock должен уметь flush, пауза/отзыв не перекрашивают старые события новым consent/dev контекстом. Не утверждай durable delivery для очереди только в памяти.

Meta Android 18.3.0: `ActivateApp` регистрирует lifecycle tracking, но activation/deactivation идут через `InternalAppEventsLogger`, который проверяет `AutoLogAppEventsEnabled`. При `false` один вызов ActivateApp не доказывает отправку activation. Выбери поддерживаемый маршрут явной activation/событий либо настрой автоматический сбор с отдельно проверенным исключением дублей покупок; не включай auto IAP вслепую ради activation. Проверь также очередь и сетевую отправку после отзыва, а не только ручной allow-guard. Существенные версии и поведение stubs должны совпадать с SDK.

## Проверка связей

Для каждой применимой стрелки сохрани sender/callback → receiver/API → mapping/config → receipt. Отключённая стрелка имеет причину и подтверждение отсутствия вызовов. Начальный набор:

| Поток | Контракт и типичная ошибка |
|---|---|
| Игра → AppMetrica и Adjust mirror | Независимая отправка двум получателям, одинаковый смысл события/контекст, собственные tokens, без второй отправки из native callback. Недоступность AppMetrica не останавливает Adjust. |
| MAX → reward journal → wallet/save | Только reward callback; observed, saved и ack — отдельные факты. Поздний/повторный callback, close, save failure и background идут через тот же однократный pipeline. |
| MAX → AppMetrica ad revenue | Один auto **или** manual источник на получателя. В Android 8.x проверить resolved `analytics-ad-revenue`; в Unity — features/resolver и настоящие subscriptions. |
| MAX → Adjust ILRD | Настоящий `onAdRevenuePaid`/эквивалент → `AdjustAdRevenue`, source установленной версии (Android v5: `applovin_max_sdk`), сумма/ISO currency/network/unit/placement. Custom impression event без setRevenue не заменяет ILRD и не является второй продажей. Рабочая отправка требует также настроек измерения ad revenue в Adjust. |
| Adjust → Axon/AppLovin и другие партнёры закупки | Сохранённые Active/data sharing, правильная app/account binding, разрешённые поля и purchase mapping; [superleo-adjust.md](superleo-adjust.md). Mediation app и закупочный partner — разные сущности. Token/SDK init не включают dashboard sharing автоматически. |
| Play → Multicast → wallet → monetary sinks | Только проверенная новая покупка; реальная цена/валюта, payment/transaction correlation, один источник для каждого AppMetrica/Adjust/Meta. Restore/replay/sandbox не создают новую выручку. Claim/consume и analytics retry независимы. |
| Multicast/backend → Adjust/Meta и client → те же sinks | Выбери один денежный путь или реально доказанную удалённую дедупликацию; имя одинакового события само её не обеспечивает. Backend registration не доказывает отключение S2S revenue. |
| Meta SDK + Adjust→Meta purchase feed | Если оба передают ту же покупку, проверь поддерживаемый event/transaction ID и факт дедупликации либо оставь один маршрут. Install-only feed не считается второй денежной отправкой. Доступ Meta/MAX — через панель согласно SKILL.md. |

Correlation ID соединяет этапы одного показа; deduplication ID различает **отдельные события**. Проверь область уникальности SDK: в Adjust Android v5.8.0 список dedup IDs общий для событий. Один `show_id` в `ad_completed`, `reward_received`, `ad_reward_saved` подавит часть воронки; используй устойчивый `event_name + ':' + show_id` при необходимости дедупликации. Для денег — собственный transaction/payment ID и durable journal; ограниченный SDK cache не заменяет ledger. Fixture должен моделировать реальную область дедупликации, а не просто считать вызовы trackEvent.

## Проверки и отчёт

До изменения прочитай callers, native config, manifest providers, subscribers и денежные backend routes. Запусти штатные проверки против реального игрового pipeline; адаптерные stubs обязаны отвергать существенные недопустимые параметры, а compile — использовать настоящие API. Воспроизведение одного дефекта в probe не закрывает упавший suite. Для отказов проверь load/init/error/timeout, revoke/regrant, background/resume, duplicate/late callbacks, disk failure и restart в затронутых цепочках, без выдуманных успешных покупок в live системе.

Отчёт содержит две таблицы: **SDK** (`version/config/code/compile/init/use/delivery/device/backoffice`) и **связи** (`sender→receiver`, source, mapping, dedup, result/evidence). Укажи artifact/package/version/hash и freshness каждого evidence, severity/файл/строку/следующий шаг дефекта. Старая запись кабинета остаётся исторической, локальный fixture — локальным. Доступный кабинет перечитай безопасной read-only операцией; недоступность фиксируй конкретно. Не запрашивай перенос сессий повторно, если нужные MCP-чтения уже работают.

QA-артефакт для получения device evidence может идти в разрешённый internal, сохраняя открытые gates. Известная ошибка интеграции не становится «готово» из-за подписи AAB, ручного READY-флага или разрешения оператора выпустить непроверенное. Внутренний трек не выключает покупки. Для подтверждения дефекта не нужно менять цены, создавать новые apps или пересобирать рабочую рекламу.
