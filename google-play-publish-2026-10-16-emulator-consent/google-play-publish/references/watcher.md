# Наблюдатель за релизом

После отправки в production отдельный долгий процесс ждёт апрув Google, реагирует на реджект и затем в сторе повторно проверяет рекламные сети и покупки. Реклама и сети часто ломаются уже после выхода приложения, поэтому проверка один раз не считается. Основной агент после сводки (шаг 12) свободен; наблюдатель диалог не блокирует.

## Запуск

1. Сразу после отправки в production создай `release/google-play/watch.json` из [watch.example.json](../assets/watch.example.json): package, track, `version_code`, `aab_sha256`, `submitted_at`, `phase: "review"`. Сохрани путь в `workflow.watch.state_ref`. Всё состояние лежит в файле, поэтому наблюдателя продолжит любой чат или машина, а каждый тик выполняется повторно без вреда.
2. Заведи повторный запуск планировщиком среды: в Claude Code `/loop` (ScheduleWakeup) или CronCreate, в Codex и других агентах их automation/heartbeat. Промпт тика: «Ты наблюдатель релиза google-play-publish. Прочитай release/google-play/watch.json и references/watcher.md. Выполни только следующую просроченную проверку, запиши результат и next_check_at, при проблеме действуй по разделу реакции. Если phase = done, останови расписание».
3. Планировщика нет → скажи оператору одной строкой, как возобновить («продолжи наблюдение по watch.json»), и остановись. Не жди sleep-циклом внутри основного диалога.
4. Только internal релиз наблюдателя не запускает (апрува нет). `update` его запускает.

Наблюдатель не запускает и не перезапускает эмулятор автоматически: каждый запуск требует отдельного вопроса оператору и явного согласия по [emulator.md](emulator.md). Без согласия продолжай проверки Console/кабинетов, а требующие эмулятора оставь `unknown` с причиной. Согласие на публикацию или прошлый запуск не переносится на тик наблюдателя.

Для проверок нужны agentb с живыми сессиями (`sessions --check`, [browser.md](browser.md)), панель SuperLeo и, для установки из Play, устройство или эмулятор с Play Store на ПК.

## Фаза review: ждать апрув

Опрос: Console → Publishing overview и Releases → Production, строго по `version_code` из `watch.json`, а не «любой статус». Частота: каждые 20 минут первые 3 часа, затем раз в час. Планировщик живёт до 7 дней; если ревью дольше, сообщи «всё ещё на ревью» и спроси, продлевать ли.

- In review: ничего не делай, обнови `last_checked_at`.
- Approved или Available on Google Play: `phase: "live_checks"`, уведоми оператора коротко.
- Rejected, Update rejected, Policy status «Issues found»: реакция ниже.

Оператора уведомляй (PushNotification или сообщение) только при смене фазы и при проблемах.

## Реакция на реджект

Прочитай причину целиком (Policy status, письмо в Console), запиши цитату в `review.rejections[]`, затем:

| Причина | Действие |
| --- | --- |
| Метаданные листинга: скриншоты, описание, иконка, контакты | Исправь в листинге и отправь заново |
| Декларации не совпадают с поведением: Data safety, Ads, Target audience, App access, Privacy Policy | Приведи формы к фактическим SDK и [data-safety-defaults.md](data-safety-defaults.md). Аудиторию 16+ и юридические страницы молча не меняй |
| Технические: permissions, target API, 16 KB, подпись, Billing | Нужен новый AAB: режим `update`, новая версия |
| Нарушение политики контента, рекламы или покупок, либо причина неясна | Не правь вслепую: оператору с цитатой и вариантами |

Автоматически отправляй повторно не более одного раза (`resubmits`). Тот же реджект после правки → `phase: "needs_operator"`. О каждом реджекте и принятом действии сообщай оператору.

## Фаза live_checks: двойная проверка в сторе

Расписание от момента, когда страница доступна и Install работает: сразу, через 2 часа, через 24 часа, через 72 часа. Каждый раз проверяй production-сборку из стора, не internal.

1. **Страница и установка.** Страница открывается, Install доступна, версия равна `version_code`. Установи из Play (не sideload) на устройство или эмулятор с Play Store.
2. **Реклама по сетям.** Rewarded загружается и показывается; смотри каждую включённую сеть отдельно (MAX Mediation Debugger или лог `MC`: load, show, reward, ошибка с кодом), а не «одна сеть сработала». Статусы в панели: AdMob остаётся `ACTION_REQUIRED` до привязки к опубликованному магазину, после выхода привяжи и сохрани `project_network_ids` ([superleo-ads.md](superleo-ads.md)); Mintegral, Pangle, Unity: приложение и placements активны и не ждут проверки. Если у кабинета есть запросы и fill, сравни с прошлой проверкой: fill 0 при заметных запросах — сбой. Не кликай по реальной рекламе, не добавляй устройство в test devices.
3. **Покупки.** Под аккаунтом license tester пройди покупку каждого типа товара из каталога: серверная валидация Multicast, однократная выдача награды, событие `purchase` в Adjust и AppMetrica ([analytics.md](analytics.md)); товары активны в Console, цены есть; отмена и ошибка обрабатываются.
4. **События и стабильность.** События доходят из production-установки; в Play Console (Android vitals) и в логе нет всплеска crash и ANR.
5. **Закупка, если идёт трафик.** В Datascape по app token есть установки и клики по ссылкам сетей; у каждого партнёра с ссылкой на игру data sharing **Active** ([superleo-adjust.md](superleo-adjust.md#партнёры-закупки-data-sharing-обязательно)); вчерашний ad spend сети пришёл. Сопоставь платформу/страны кампаний с ABI и production Device catalog текущего AAB. При низкой конверсии клика в установку сначала проверь потерю 32-битного Android, новые Unsupported/exclusions и доступность Install в целевых гео ([инцидент «Свинок»](play.md#архитектуры-abi-arm64-и-другие)); не объявляй это проблемой креативов без проверки совместимости.

Результат каждой проверки: `pass`, `fail` или `unknown` с доказательством. Нет устройства или доступа → `unknown`, не `pass`.

## Реакция на сбой после выхода

| Проблема | Действие |
| --- | --- |
| Клики есть, конверсия в установку низкая | Проверь ARMv7+ARM64 и полный runtime production AAB, Device catalog, гео/minSdk/required features и Install для целевых устройств; сравни с предыдущей версией. Исправление ABI требует нового AAB, не повторной отправки метаданных. Не смешивай недоступность установки с отсутствием атрибуционных постбэков |
| Сеть не отдаёт рекламу, ждёт привязки или проверки | Исправь привязку или placement через панель, остальные сети продолжают работать, перепроверь через час. Сеть молча не отключай |
| Rewarded не работает ни в одной сети | Критично: сразу оператору. Причина (SDK key, consent, adapter), исправление через `update` |
| Покупка не проходит, награда не выдаётся или выдаётся дважды, валидация падает | Критично: сразу оператору и предложение остановить rollout (Halt в Console) до исправления. Останавливай только с разрешения оператора или по заранее данному |
| События не приходят | Токены и конфиг; нехватка доступа к Adjust → `waiting_for_access`, сама по себе не блокер |
| Трафик идёт, а в кабинете сети нет установок/ROAS | Data sharing партнёра в Adjust выключен: включи по [superleo-adjust.md](superleo-adjust.md#партнёры-закупки-data-sharing-обязательно) и сообщи оператору, что прошлые постбэки не вернутся |
| Всплеск crash или ANR | Критично, как выше |

Правка кода — новая версия по правилам update; для неё наблюдатель стартует заново.

## Завершение

После проверки через 72 часа (все `pass` либо оформленные проблемы) ставь `phase: "done"`, останови расписание и дай оператору короткий итог: сети и покупки, что исправлялось, что ждёт решения.
