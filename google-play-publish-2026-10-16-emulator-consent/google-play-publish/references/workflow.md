# Сценарий по шагам

Все действия в Google Play Console и кабинетах выполняются через CLI agentb ([browser.md](browser.md)); серверный воркер SuperLeo `play_*` только запасной. Порядок запуска для `release`/`full`. Каждый шаг пишет в `workflow.step` профиля и в `status.md` свой статус и доказательство. Независимые части идут параллельно ([execution.md](execution.md)); вопрос оператору задаётся только там, где он указан, одним сообщением. Во всех шагах действует принцип: сначала найди готовое (профиль, сервисы, формы, assets), создавай только недостающее.

## Что запускать при update

| Шаги | `release` | `update` |
| --- | --- | --- |
| 1–2 Игра и решение по монетизации | да | только если менялась реклама/магазин |
| 3 Реализация монетизации | если выбрана | только изменённые части |
| 4–5 Сервисы и приложение в Play | создать/переиспользовать | не повторять; проверь package и права |
| 6 Аналитика, логирование, dev | да | только изменённые события и dev-доступ |
| 7 Иконка, баннер, скриншоты | да | только если изменились визуалы/текст/механики |
| 8–9 Билд, internal, IAP | да | новая версия; регистрацию IAP повторять только при изменении каталога, checkout/recovery проверять и при неизменных SKU |
| 10–11 QA и production | да | да, по тем же gate |
| 12 Сводка | полная | изменения и ссылка на прежнюю таблицу |
| 13 Наблюдатель | да | да, проверки рекламы и покупок на новой версии |

## 1. Играй и пойми игру

Запусти игру доступным способом (Editor/MCP, устройство через ПК, браузер для веб-игры; эмулятор — только после отдельного согласия на каждый запуск по [emulator.md](emulator.md)) и проведи минимум 2–3 минуты настоящей игры. Снимай кадры: они же пригодятся для концепта и оформления. Запиши в профиль краткий `game_brief`: жанр, core loop, управление, экономика, существующие валюты. Отдельно найди и отметь: есть ли **rewarded-оффер** (видимая кнопка/иконка «за видео» с наградой) и есть ли **магазин товаров** (вход с HUD и панель с товарами). Не опирайся только на код: оффер и магазин должны быть доступны игроку в билде.

## 2. Решение по монетизации

- **Оба есть:** сразу шаг 3 только для недостающих проверок.
- **Нет оффера и/или магазина:** задай оператору один вопрос с вариантами: ввести rewarded / ввести магазин / ввести оба / публиковать пока без рекламы и/или инапов. Рекомендация по умолчанию — ввести то, чего нет.
- **«Ничего не надо»:** релиз ограничен аналитикой (Adjust, Meta) и выкладкой в стор. MAX, mediation, IAP и их формы Console не создаются; Ads/In-app purchases в Console и Data safety заполняются по факту.
- **Что-то выбрано:** предложи план. Если у текущей модели есть генерация изображений (внутренний `imagegen`/`image_gen`, либо DostupAI через `hub_tools_search`), сгенерируй концепт-кадр от настоящего скриншота игры: как в её стиле выглядит rewarded-оффер и/или панель магазина. Иначе опиши текстом коротко: где вход, что за награда, какие товары, какие уже существующие спрайты и панели переиспользуем (найди их в проекте). Награды и IAP-каталог (ID, тип, содержимое, цена, регионы) — предложение владельцу; его ответ на это сообщение и есть согласование каталога, сохрани дату и ссылку на сообщение ([state.md](state.md)).

## 3. Реализуй выбранное

Подключай к настоящему bootstrap/UI/save, не рядом с игрой. Rewarded: награда только от коррелированного reward callback, однократно и с durable save ([sdk-validation.md](sdk-validation.md), [superleo-ads.md](superleo-ads.md)). Магазин: [play.md](play.md#магазин-в-самой-игре); покупки с серверной валидацией Multicast ([server-iap.md](server-iap.md)). SDK и мосты выбирай по [engines.md](engines.md), эталон — [devour.md](devour.md). Реклама и покупки не мешают игре: ошибка сети не блокирует вход и награды.

## 4. Сервисы через панель

Создай или переиспользуй приложение игры в Adjust, Meta и (если есть реклама) в MAX с mediation-сетями. Порядок: прочитать каталог и существующие записи → переиспользовать совпадения по package → создать недостающее → прочитать обратно → внедрить IDs в игру. Маршрут: SuperLeo MCP ([superleo.md](superleo.md)), для неподдерживаемых операций браузерная панель ([panel-preflight.md](panel-preflight.md)). Браузер — agentb ([browser.md](browser.md)); сохранённые входы переиспользуются; первый перенос в рабочей сессии — `login-hub` со штатным согласием владельца. MAX и Meta — только через панель Multicast. Не заводи приложение вручную, если есть операция каталога; не трать время на разведку UI, если контракт уже описан. Каждый результат сохраняй отдельно, отказ одного сервиса не останавливает остальные.

Обязательная часть настройки Adjust: data sharing для партнёров закупки (Axon by AppLovin с account MAX SDK key, Sessions, Uninstalls, Parameters и In-app revenue через событие `purchase` → In-App Checkout) с readback **Active** — [superleo-adjust.md](superleo-adjust.md#партнёры-закупки-data-sharing-обязательно). Без него трафик идёт, а сеть не получает установок и выручки.

## 5. Приложение в Google Play и формы без билда

Создай приложение под аккаунтом сотрудника Multicast Games ([browser.md](browser.md); запасной маршрут [superleo-play.md](superleo-play.md)); если вход требует действия владельца, запроси ровно его. Заполни всё, что не зависит от билда и графики, «в лёт» по единому шаблону студии:

- аудитория 16+, не детская; контакты, сайт, Privacy Policy и Terms — из [правил студии](../SKILL.md#правила-студии), ничего не спрашивай;
- по умолчанию реклама и покупки есть (Contains ads — Yes, In-app purchases — Yes). Если на шаге 2 выбрано «без», отмечай по факту;
- Data safety, Ads declaration, Content rating, App access, Government/Finance/Health и прочие формы: переиспользуй ответы соседнего приложения студии, [data-safety-defaults.md](data-safety-defaults.md) и профили `<agentb>/scenarios/profiles/*.json`, сверяя с SDK этой игры. Быстрый путь — `play_data_safety.py` и `agentb run <профиль>.json` ([play.md](play.md#формы-и-выпуск)); CSV и профили из предыдущих приложений — шаблон, не копия вслепую;
- не доходи до сборки и графики: они на шагах 7–9.

Одна вкладка Console, один процесс автоматизации, пакетное заполнение: все поля → save → reload → readback.

## 6. Аналитика, логирование и dev-доступ

Перед реализацией составь карту SDK и потоков по [sdk-interactions.md](sdk-interactions.md). У каждого применимого сервиса и связи должны быть исходник/конфигурация, ожидаемое поведение и отдельный результат: compile, init, use, delivery. При update повтори затронутые связи по fingerprint ([execution.md](execution.md)); неизменный каталог не освобождает от проверки purchase flow, SDK/bridge/consent и smoke новой Play-установки.

Подключи события к реальным действиям по [analytics.md](analytics.md), [events.example.json](../assets/events.example.json) и [sdk-validation.md](sdk-validation.md): **в AppMetrica** (основная, полный JSON-контекст) и **зеркалом в Adjust**: Adjust повторяет весь аналитический слой игры под теми же именами событий, по одному токену на имя, события без токена не уходят ([analytics.md](analytics.md), шаблон `assets/AdjustEventMirror.cs.txt`). Полный набор: жизненный цикл и `time_spent` раз в минуту, все состояния рекламы (`ad_*`, включая `ad_reward_saved`), прогресс, экономика, покупки (`iap_*`) и отдельное `purchase` с revenue. Реклама: попытка, успешный показ, неуспешный (код), выданная награда, закрытие без награды, revenue. Покупки: открытие магазина, старт, pending, серверная валидация, выдача, отмена, ошибка, restore, revenue. Сессия, плейтайм, init каждого SDK. Токены заведи в кабинете Adjust через agentb ([browser.md](browser.md)): импорт из приложения-образца или цикл Add event ([analytics.md](analytics.md)); нет доступа, ставь `waiting_for_access` и иди дальше. Лёгкий лог и автоматические dev-кнопки у HUD — [dev-mode.md](dev-mode.md). Для одного AAB проверь доступ тестера и отсутствие инструментов у обычного игрока; реклама, IAP и аналитика в обоих случаях работают одинаково. Не добавляй ручную активацию.

### Токены Adjust (внутри шага 6, до финальной сборки)

Токены вшиваются в билд через конфиг, поэтому их заводят **до** шага 8. Проверено на Piggy Payday: 50 событий и чтение токенов заняли около 5 минут активной работы.

1. Возьми имена из `adjustEvents` конфига игры; токен `purchase` живёт в `adjustPurchaseToken`, его в кабинете не дублируй. Открой `https://suite.adjust.com/apps/<adjustAppToken>/events` через `agentb text --url ...` ([browser.md](browser.md)) и посмотри, какие события там уже есть.
2. Заведи недостающие: `agentb run scenarios/adjust_events_create.js --url <страница Events> --set-file NAMES=<names.json>`, пачками до 25 имён на вызов. Форма Add event: имя, остальное по умолчанию (*unique* не включай, проверки Source/Flow/Revenue выключены).
3. Прочитай таблицу: `agentb run scenarios/adjust_events_read.js --url <страница Events>` (список виртуализован, скрипт прокручивает его сам). Сохрани результат как `release/google-play/adjust-tokens.json` вида `{"имя": "токен"}`, число пар должно равняться числу событий плюс `purchase`.
4. Впиши токены: `python scripts/fill_adjust_tokens.py <GameServiceConfig.json> release/google-play/adjust-tokens.json`. Скрипт не затирает другой стоящий токен, показывает события без токена и лишние имена.
5. Нет входа в Adjust или нет прав: токены `waiting_for_access`, сборка идёт с пустыми (события не отправляются), а в сводке это отдельная строка.

## 7. Иконка, баннер, скриншоты

[store-assets.md](store-assets.md): иконка и feature graphic, скриншоты из настоящего геймплея с короткими подписями **на английском** в стиле игры. Если у текущей модели нет генерации изображений, не подменяй её рисованием SVG: предложи оператору переключиться на модель с генерацией или сгенерируй через DostupAI (`hub_tools_search`, сервис `dostupai`), затем осмотри результат. Launcher icon внутри AAB назначай отдельно.

## 8. Билд в internal

Выбери `versionName` как `крупное.среднее.мелкое` по [правилу версий](play.md#версии-major-minor-patch): крупная версия 2 записывается `2.0.0`. Отдельно выбери свободный возрастающий `versionCode` по Console и локальным артефактам; тот же AAB при продвижении версии не меняет.

До сборки сверь платформу/гео закупки и охват устройств. Один Play AAB сразу содержит ARMv7 + ARM64; после сборки проверь полный runtime обеих ABI в файле, после обработки Console — production Device catalog и изменения охвата. ARM64-only без явного решения об ограничении аудитории не проходит этот gate. История «Свинок» и конкретные проверки — [play.md](play.md#архитектуры-abi-arm64-и-другие); проверки обязательны и при update, чтобы не вернуть потерю конверсии WW-трафика.

До финальной сборки закрой статические и локальные проверки [SDK-контрактов](sdk-interactions.md) и [checkout](server-iap.md#google-play-checkout-до-сборки). Успешная сборка не заменяет их. Если штатный набор тестов падает до проверяемых сценариев, восстанови стенд и повтори; временные заглушки и отдельный probe не превращают полный suite в PASS. Блокирующий дефект кода не переименовывается в «ожидает устройства».

Все правки кода, иконки и версия готовы → одна финальная release-сборка ([execution.md](execution.md), [play.md](play.md#android-требования)). Если есть реклама или покупки, до сборки проверь (и что токены Adjust уже в конфиге, шаг 6): Billing Library и `com.android.vending.BILLING` в merged manifest, production SDK-конфиги, consent-флоу (нативное окно согласия на рекламу появится при старте), `versionName` и `versionCode` выше всех занятых. Пока идёт сборка, заполни всё остальное, кроме загрузки билда: текст листинга, графику, тестеров, оставшиеся формы. Сборку держи фоном.

## 9. Загрузка в internal и покупки

Загрузи подписанный AAB в internal и выпусти ([browser.md](browser.md): файл подставляется с диска ПК одним вызовом). Сохрани opt-in ссылку. Раз билд с Billing теперь в сторе, раздел Monetization доступен: заведи согласованные IAP-продукты одним проходом и зарегистрируй их с серверной валидацией Multicast ([superleo-iap.md](superleo-iap.md), [server-iap.md](server-iap.md)), затем readback каждого SKU. Если ID в билде совпадают с созданными, пересборка не нужна. Нет покупок: шаг пропускается.

## 10. QA перед production

Сохрани SDK-матрицу и результаты связей по [sdk-interactions.md](sdk-interactions.md), включая MAX → ILRD → Adjust и Adjust → партнёры. «Реклама работает» подтверждает наблюдавшийся формат/показ, но не остальные сети, consent, денежные sinks или покупки. В отчёте отдельно перечисли известные дефекты и непроверенные runtime-факты. Разрешение владельца продолжить релиз не меняет failed/pending проверки на verified.

Предложи оператору поиграть в билд из internal; при доступном устройстве или установке из Play проведи проверку сам. Каждый запуск/перезапуск эмулятора предварительно согласуй отдельно по [emulator.md](emulator.md); не запускай его автоматически ради этого gate. Если поручено только опубликовать без runtime-прогона, переходи к шагу 11, сохранив непроверенные пункты. Gate зелёный, когда подтверждены на **этом** артефакте: rewarded показывается и награда выдаётся один раз; покупка проходит (license tester) с серверной валидацией и однократной выдачей; события доходят до AppMetrica/Adjust; в логе нет необъяснимых ошибок (crash, ANR, провал init SDK); игра нормально играется минимум 2 минуты. Недоступное остаётся `waiting`, не `verified` ([verification.md](verification.md)).

## 11. Production

Тестировал сам и gate зелёный → отправь **тот же AAB** в production без пересборки, заверши save → submit → confirm → readback (статус In review). Если runtime-проверки не выполнены, но оператор уже явно поручил выпустить без прогона (например, «сейчас не надо, просто отправь в паблиш и internal»), отправь тот же AAB в разрешённые треки без повторного вопроса и без запуска эмулятора. Зафиксируй поручение, пропущенные проверки и риск; их статусы не становятся verified. Иначе, если gate не зелёный или проверить не удалось, спроси оператора, играл ли он и готов ли публиковать, и действуй по ответу. Известный дефект не переименовывай в пропущенную проверку. Не публикуй при `publication_hold`, при незаполненной обязательной форме листинга или если поручение ограничено internal. После отправки сразу выдай сводку (шаг 12) и заведи наблюдателя (шаг 13); апрува не жди в основном диалоге.

## 12. Сводка

Короткий блок по [handoff.md](handoff.md): bundle, версия и SHA-256, keystore (путь, alias, пароли), Meta/FB IDs, AppMetrica app ID и SDK key, Adjust, AppLovin MAX и сети, IAP, трек и статус.

## 13. Наблюдатель

Отдельный долгий процесс ([watcher.md](watcher.md)): ждёт апрув production, при реджекте читает причину и действует по таблице, после выхода в стор повторно проверяет **каждую рекламную сеть и покупки** через сразу, 2 часа, 24 часа и 72 часа, потому что сети и покупки часто ломаются уже после публикации. Состояние живёт в `release/google-play/watch.json`, поэтому наблюдателя может продолжить любой чат. Критичные сбои (rewarded, покупки, crash) сразу идут оператору.
