# Профиль и возобновление

Режимы и применимость заданы в [../SKILL.md](../SKILL.md); правила reuse/таймингов — [execution.md](execution.md). В update сохраняй выполненные независимые этапы, инвалидируя только изменившиеся входы. Marketing-поля обязательны для заказанного marketing/full; они не заставляют переснимать материалы каждого release. Старое runtime evidence и smoke нового артефакта фиксируются раздельно. Прогресс сценария ведётся в `workflow` профиля: `step`, `monetization_decision` (есть ли rewarded и магазин, ответ оператора, ссылка на концепт), `dev_tools` (автоматический источник статуса тестера, кнопки у HUD, отдельные проверки тестера/игрока, ссылка на лёгкий лог), `publish_to_production`, `qa_gate_ref`, `watch` (состояние наблюдателя, [watcher.md](watcher.md)) по [workflow.md](workflow.md).

Настройки конкретной игры: `release/google-play/profile.json`, журнал: `release/google-play/status.md`. Форма — `../assets/profile.example.json`; `null` означает неизвестное, а не shipping-значение. Профиль игры не меняет глобальные правила скилла.

Храни package name, движок/Android wrapper, internal-трек, приложения провайдеров и ссылки на конфигурацию, рекламные форматы, версии SDK/адаптеров, согласованный каталог и группу тестеров. Публичные ID допустимы в конфигурации проекта. Пароли keystore, private keys, service-account JSON, access tokens и backend secrets храни средствами секретов проекта/CI/ОС; профиль содержит только ссылки. Credential-файлы не входят в Git или пакет скилла.

Если владелец поручил сохранить доступы для продолжения, используй отдельный локальный `release/google-play/access.local.json`, исключённый из Git и архива скилла. Сохраняй только нужные этому workflow подключения, SDK-конфигурацию и ссылки на session state. SDK API key AppMetrica (UUID) не является числовым App ID кабинета или OAuth-токеном управления: сохраняй назначение поля, не подставляй его в `app_id`. Правила доступа к существующему Chrome и переноса сессий: [panel-preflight.md](panel-preflight.md).

При первом запуске и ошибках авторизации применяй [service-access.md](service-access.md): агент сам запрашивает недостающие доступы, а после получения продолжает создание/настройку. В `service_access.checks` храни только статусы, права, account/secret refs и доказательства; в `service_access.pending_requests` — какие доступы запрошены и какой шаг возобновить. Не оставляй единственную запись «нет доступа» без конкретного запроса. Закрытый запрос не означает проверенное создание приложения или получение событий.

Для локального заполнения можно скопировать [access.example.json](../assets/access.example.json) в ignored `release/google-play/access.local.json`. Это private конфигурация текущего пользователя; её значения не переносятся в публичный профиль, приложение или архив. Подключай только нужные поля выбранного маршрута, не требуй заполнить весь шаблон. Environment/secret-manager refs также допустимы.

Для этапа запиши статус (`not_started`, `in_progress`, `verified`, `waiting_for_user`, `waiting_for_access`, `waiting_for_device`, `failed`), доказательство и следующий шаг. Код, конфигурация, сборка, device QA и внешний релиз имеют отдельные статусы. Лог попытки отправки не доказывает получение события сервером.

В `store_assets` сохраняй язык, ссылку на manifest/пакет, отдельные статусы готовности файлов и загрузки в Console. Manifest содержит порядок, подписи/alt text, размеры/формат, SHA-256 и происхождение игровых кадров. Использованный внутренний генератор и финальные промпты фиксируй рядом с файлами; локальные изображения не означают сохранённую страницу магазина. Workflow — [store-assets.md](store-assets.md).

В `marketing` сохраняй выбранный playable-сегмент и причину, три сюжета, язык/размер/fps/длительность, пути raw/final, происхождение видео/звука/ресурсов, staging-сохранение, SHA-256, техническую проверку и полный просмотр каждого видео. Playable: отдельные сетевые targets, HTML/ZIP, byte budgets, offline/touch/CTA/lifecycle/browser receipts и статус кабинетной валидации. Инструкции — [marketing-creatives.md](marketing-creatives.md), [playable-contracts.md](playable-contracts.md). После записи восстанови состояние Editor и указатель сохранения; собственные QA-параметры не переносятся в production.

После setup или изменения интеграций обновляй полный отчёт приложений и mediation по [handoff.md](handoff.md); в update неизменной интеграции переиспользуй подтверждённый отчёт и записывай только изменения. Сохраняй SDK identifiers этой игры в ignored `service-handoff.local.json`/`.md`, публичный профиль — только ссылки и статусы. После setup/изменения интеграций итоговый ответ содержит актуальные AppMetrica/Adjust/MAX IDs и подключённые сети; update неизменной интеграции показывает изменения и ссылку на подтверждённую таблицу. Перед упаковкой исключи оба отчёта и все доступы пользователя.

Согласование товаров — точная таблица, дата и ссылка/описание сообщения пользователя. Boolean `approved` сам по себе не подтверждает согласование. Изменение ID, типа, награды, цены, валюты или регионов требует новой принятой таблицы. Цены UI берутся из магазина.

В журнал не включай секреты и сырые чеки. Для диагностики транзакции используй безопасную ссылку/идентификатор. Для AAB сохрани путь, SHA-256, package name, versionCode и публичный fingerprint upload-сертификата.

Повторный запуск сверяет кабинеты и локальное дерево, переиспользует совпадающие записи и не доверяет старой пометке `verified` без проверки изменившихся частей. После таймаута ищи результат по устойчивому ID перед повторной записью. Изменение цели обновляет профиль с сохранением выполненных независимых этапов.

При MCP сохраняй `panel_connections[]`: endpoint, actor email, role/capabilities, project ID, checked_at, safe evidence_ref, private config_ref. Разные подключения не разделяют IDs по умолчанию. `providerValidated:false`/план не является созданием; draftSaved не является released. Для uncertain writes сохраняй стабильный requestId, package/version/hash и receipt/journal refs. Raw MCP responses/SDK keys держи в ignored private файлах, не в этом профиле.

## Manifest и доказательства каждого этапа

Перед работой сохрани `stages.<stage_id>` в профиле: `status`, `requirements_manifest_ref`, `evidence_ref`, `next_step`. Manifest перечисляет scope (приложение/версия/локаль/сервис), каждое требование и применимость с источником, ожидаемый результат и способ проверки. Evidence содержит реальные результаты по тем же ID, время и ссылки на raw native receipts: Editor/build/device logs для native этапов, кабинет/API save + readback для внешних записей. Не придумывай measurements, receipts, screenshots или успешные ответы. На каждом этапе сверяй множество требований с множеством проверок; missing/unknown/failed/pending блокируют завершение. Изменение scope/manifest делает прежний gate устаревшим.

`verified` и пользовательские синонимы `complete`/«готово» разрешены только после прохождения всех применимых требований. Подготовленная конфигурация не означает runtime verification; SDK key не означает third-party access; локальный asset не означает Console save. Для недоступного сервиса сохраняй `waiting_for_access` и точный следующий шаг; для upload — `pending_upload`, для неизвестного — `in_progress`. Продолжай независимые этапы, но не повышай общий статус готовности при открытом обязательном пункте. `not_applicable` требует evidence причины и не служит обходом отказа доступа.

`store_assets` отдельно хранит asset manifest, `form_inventory_ref`, `required_fields_evidence_ref`, save/reload/readback evidence refs и `completion_gate_status`. Inventory строится по реальной Console для каждой listing/локали; начальные phone/tablet_7/tablet_10 checks в примере профиля **не являются наблюдением**. Gate проверяет весь inventory, включая визуальные поля выбранных целевых категорий и явно исключённые необязательные категории, и не ограничивается шестью previews. У каждой категории отдельные expected/observed counts, размеры/формат, mapping и upload/readback status; применимое пустое поле не может быть verified. Профиль хранит ссылки на подробности по [verification.md](verification.md), а не копию credentials или сырых приватных ответов.

## Состояние функциональных SDK gates

`sdk_validation` в примере профиля задаёт ссылку на [sdk-validation.md](sdk-validation.md) и пустой `checks` для каждого провайдера. Заполняй только применимые проверки: `presence`, `compile`, `own_config`, `init`, `use`, `delivery`, `device`, `backoffice`; проверка содержит `status`, `evidence_ref`, `next_step` и scope (package/артефакт/version/environment). Не копируй успешные статусы из референса. До наблюдения — `unknown`/`in_progress`, при ожидании — соответствующий waiting/pending, при ошибке — `failed`; `verified` требует фактического evidence. Одного provider status или app ID недостаточно.

`ads.enabled_formats` отражает принятое включение, `ads.disabled_formats` — явное отключение; `null` означает неизвестное. Rewarded обязателен. Optional interstitial/banner вне scope получают `not_applicable` со ссылкой на решение пользователя и проверкой отсутствия placement init/load/show, а не `failed` из-за пустого ID. Проверки SDK/mediation/дохода охватывают включённые форматы.

Сохраняй источник и наследование уже данного согласования в `release.authorization_evidence_ref`; не спрашивай заново об уже разрешённых записях. `release.publication_hold` не снимается успешной сборкой/QA или прежним разрешением: явное возобновление владельцем обязательно. Эти поля в шаблоне неизвестны, их нельзя трактовать как согласие. Статус internal release и статус runtime/device/backoffice verification независимы; internal для получения QA не превращает pending интеграцию в готовую.
