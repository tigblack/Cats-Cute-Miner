# Multicast → Google Play

Доведи текущий проект до внутреннего теста Google Play. Исправляй неполные интеграции самостоятельно и сохраняй результат для продолжения следующим агентом. Одна команда запускает весь процесс; согласование требуется для каталога инапов, неизвестных продуктовых решений и production, если его ещё не поручили.

**Доступы запрашивает агент.** Проверь уже предоставленные подключения, затем сам собери и запроси недостающие доступы к панели, AppMetrica, Adjust, Meta, MAX/сетям и Google Play по [references/service-access.md](references/service-access.md). После получения продолжи создание приложений и интеграцию; не оставляй владельцу задачу завести приложения и вручную принести SDK keys. Доступы персональны для каждого использующего скилл и не входят в его архив.

**Первый запуск у другого сотрудника:** рабочая панель — https://dostupai.aimulticast.org/ либо явно предоставленный ему endpoint. Если готового MCP/config нет, открой панель в одной вкладке и попроси сотрудника войти своим предоставленным аккаунтом; затем проверь доступные операции. MCP-ключ не обязателен для browser workflow. Не отправляй сотрудника в ненаблюдавшийся раздел Admin и не ссылайся на private файлы/почту ПК предыдущего владельца. Запрашивай дополнительный доступ только для конкретной операции, которую не удалось выполнить через его доступный маршрут.

## Правила студии

- Во **всех** проектах обязательны **AppMetrica + Adjust + Facebook/Meta App Events + AppLovin MAX**. Работающие дополнительные сервисы сохраняй; они не заменяют обязательные.
- Общие ссылки студии для всех проектов: **Privacy Policy — https://multicastgames.com/policy**, **Terms of Use — https://multicastgames.com/termsofuse**. Используй в игре, штатном consent flow и формах магазина; не запрашивай их заново. Принятие Terms не подменяет согласие на передачу данных.
- Эталон — **`Z:\Repos\devour\Devour.Unity` на ПК пользователя**. Самостоятельный снимок контракта и проверенных версий: [references/devour.md](references/devour.md). Он позволяет работать без доступа к референсу на каждом запуске.
- Панель — административная прослойка для приложений, сетей и рекламных блоков. Используй **личное предоставленное подключение текущего пользователя**; email предыдущего пользователя не является студийным default или требованием. Основной UI: `https://dostupai.aimulticast.org/`; MCP этого UI: `https://dostupai.aimulticast.org/mcp`. Исторический Railway endpoint применяется только при отдельно предоставленном подключении, без переноса ключа между серверами. Клиент и контракты включены: сначала читай [references/superleo.md](references/superleo.md). Browser UI — рабочий маршрут при отсутствии MCP либо нужной операции. SDK/адаптеры — из проекта или официальных источников; UI описан в [references/panel.md](references/panel.md).
- Тестеры internal: если не задана конкретная группа, подключи **все существующие непустые списки/группы тестировщиков текущего аккаунта**. Сначала перечитай полную таблицу и текущие selections, затем сохрани и проверь каждое назначение. Не создавай новые списки/адреса автоматически; спрашивай только если подходящих списков нет или состав невозможно установить. После выпуска всегда верни рабочую opt-in ссылку. Отдельно проверяй license testing: участие в internal само по себе не делает покупки бесплатными.
- Трек по умолчанию **`internal`**. «Давай в стор» разрешает подготовку, создание необходимых записей этой игры, загрузку и выпуск во внутренний тест. Не запрашивай повторное разрешение. Production — по отдельному поручению; уже данное поручение не согласовывай повторно.
- Browser Console: работай в **одной вкладке задачи, максимум двух**. Сначала прочитай список вкладок и переиспользуй существующую; сохраняй её ID между запусками. Для перехода между формами меняй URL этой вкладки. Одновременно работает только один процесс браузерной автоматизации; перед повтором останови предыдущий и перечитай страницу. Новая вкладка при каждом запуске скрипта запрещена. Закрывай только подтверждённые дубликаты своей задачи, сохраняя остальные вкладки пользователя. Подробности: [references/play.md](references/play.md).
- Если владелец ставит публикацию на паузу, сохрани `release.publication_hold` и продолжай разрешённые локальные проверки. Не загружай билд ни в internal, ни в production, пока владелец явно не возобновит публикацию. Ранее принятое `update_tracks` не отменяет более позднюю паузу.
- **Каталог инапов согласуется**: ID, тип, содержимое/награда, цены, валюта и регионы. До согласования изучай экономику, готовь предложение и независимую инфраструктуру, но не создавай товары в консоли и не подключай предлагаемые награды к реальным продажам. Принятое согласование действует до изменения этих условий. Для денежных покупок студии обязательна **серверная валидация Multicast**; SKU в Play и локальная RSA-проверка сами по себе не завершают интеграцию.
- Самостоятельно выбери интеграцию по ядру проекта: переиспользовать имеющийся SDK, установить готовый официальный пакет либо написать свой интеграционный слой/мост. Особенно в Unity сначала проверь уже установленные SDK и их реальное подключение. Devour — образец состава, логики и внедрения в живой проект; версии/реализацию сверяй с ним, сохраняя архитектуру текущей игры. Свою реализацию проверяй по тому же функциональному контракту. Имитация SDK, логирование вместо отправки и пустой backend не считаются интеграцией.

## Начало и продолжение

1. Прочитай правила проекта, изучи текущие изменения, сохрани чужую работу. Определи корень игры, движок, Android-обёртку, интеграции и путь сборки. В монорепозитории проверяй выбранную игру.
2. Прочитай [references/state.md](references/state.md) и [references/service-access.md](references/service-access.md). Продолжи `release/google-play/profile.json` и `release/google-play/status.md`; при первом запуске создай профиль из [assets/profile.example.json](assets/profile.example.json). Проверь права нужных операций, запроси конкретные недостающие доступы одним списком и запиши ожидаемые ответы. После получения доступа перепроверь его и возобнови зависимый этап; параллельно выполняй независимые этапы.
3. Выполни статический поиск. Если доступен Python 3:

   ```text
   python3 <путь-к-скиллу>/scripts/audit_project.py <корень-игры> --output <корень-игры>/release/google-play/audit.json
   ```

   Помощник выдаёт указатели, **не готовность к релизу**. Без Python используй `rg` или поиск платформы. Проверь coverage/exclusions: SDK в исключённом каталоге проверяется отдельно. Проверь импорты, конфигурацию, bootstrap, реальные вызовы и итоговые зависимости вручную.
4. До выполнения каждого этапа создай manifest требований и ожидаемых доказательств по [references/state.md](references/state.md). Закрывай этап только по фактическим receipts/readback: неизвестное, ожидаемые доступы и подготовленные файлы не равны `verified`/`complete`/«готово».
5. Для каждого сервиса различай: SDK/адаптер найден → API/Android compile пройден → настройки принадлежат игре → реальная инициализация успешна → функция используется → доставка подтверждена устройством и кабинетом. App IDs и наличие пакетов не закрывают последние gates; `unknown`/`pending`/`failed` остаются открытыми. Отсутствие бинарника/кэша на сервере означает «не подтверждено», пока не проверен ПК или артефакт.

На Windows-ПК MultiCode выполни read-only проверку build-машины приложенным `scripts/pc_preflight.ps1`. Из корня проекта с этим скиллом:

```text
on-remote powershell -NoProfile -ExecutionPolicy Bypass -File ".agents/skills/google-play-publish/scripts/pc_preflight.ps1" -ProjectPath . -ReferencePath "Z:/Repos/devour/Devour.Unity" -CheckDevices
```

Если референс недоступен, опусти `-ReferencePath`; путь к скрипту адаптируй к месту установки скилла. Проверка читает безопасные player settings, наличие Android-модуля/SDK platforms, инструментов и подключённых устройств. Она не подтверждает работоспособность SDK и не выводит ключи/пароли. Проверь effective package name через Editor/итоговый manifest: отсутствие явного поля в YAML не исключает engine default. `unity status` может не видеть открытый Editor без Pipeline package; сверяй процессы/доступный Editor bridge и не запускай второй batch process на занятом проекте.

Перед административными действиями прочитай [references/superleo.md](references/superleo.md); проверь account/capabilities/catalog и существующие ресурсы по package. Для browser-only маршрута используй [references/panel-preflight.md](references/panel-preflight.md). MCP endpoint, actor и project ID сохраняй отдельно: ID другой учётки/панели не переносится автоматически. Успешный вход не является доказательством доступа Adjust, регистрации AppMetrica/Meta или прав Play upload. Сохраняй отдельные результаты по операциям и продолжай независимые этапы при отказе одной интеграции.

В MultiCode синхронизируемые исходники меняй локально, команды тулчейна выполняй доступным мостом к ПК. Если есть `on-remote`, Windows-референс читай через него; не проси Git-ссылку только из-за Linux-среды. При отсутствии `rg` на Windows используй PowerShell `Get-ChildItem`/`Select-String`. Не редактируй синхронизируемые исходники одновременно на ПК и сервере.

## Интеграции и монетизация

1. Прочитай [references/devour.md](references/devour.md), подходящую ветку [references/engines.md](references/engines.md) и [references/sdk-validation.md](references/sdk-validation.md). Составь таблицу расхождений с путями и исправь её. Выбери и реализуй подходящий вариант интеграции; совместимые установленные SDK не переустанавливай и не дублируй. Учитывай native dependencies, а не только версии обёрток. Компиляция SDK-моста проверяет API, но не заменяет его вызов из bootstrap/UI и связь с сохранением игры.
2. Зарегистрируй или переиспользуй приложение **этой игры** в AppMetrica, Adjust и Meta через каталог панели: [references/superleo.md](references/superleo.md), [references/superleo-adjust.md](references/superleo-adjust.md), [references/superleo-facebook.md](references/superleo-facebook.md). Поддерживаемые панелью административные операции выполняй через неё. Когда нужной операции или рабочего upstream доступа нет, сам запроси конкретный доступ к сервису и используй его официальный API либо кабинет по [references/service-access.md](references/service-access.md), не заставляя владельца создавать приложение. SDK/документацию бери из официальных источников; не меняй настройки сетей наугад. Сверь package name/окружение. Не переноси приложенческие ключи, App ID, event tokens, ad unit IDs или SKU Devour. Account-level MAX SDK key можно переиспользовать только после проверки, что блоки этой игры и референса принадлежат тому же аккаунту; сохрани источник и доказательство, не подменяя новые ad unit IDs. При ожидании доступа продолжай установку SDK, bootstrap, событий, рекламных callbacks, HUD и проверку сборки основной игры. Настройки и инициализация провайдеров независимы: отсутствие Adjust token или Meta App ID не выключает уже настроенные AppMetrica/MAX. Создание, повторное чтение, получение own SDK credentials и внедрение выполняет агент; каждый результат сохраняй отдельно.
3. Подтверди реальную активацию AppMetrica и отправку/получение custom событий по [references/sdk-validation.md](references/sdk-validation.md). Реализуй единый слой типизированных событий с отправкой в AppMetrica. Подключи старт игры, согласие, прогрессию/экономику, рекламу и покупки к реальным действиям. [assets/events.example.json](assets/events.example.json) задаёт примеры формы; игровые имена адаптируй. Не рассылай каждое событие во все SDK без назначения.
4. Adjust: собственный token, production config, успешный init, session/attribution и ILRD с подтверждением получения. Meta App Events: собственная регистрация, package/key hashes/client token wiring, consent-aware Init → ActivateApp → выбранные события и реальная проверка сервером/Test Events. Полные gates — [references/sdk-validation.md](references/sdk-validation.md). Проверь native manifest и сбор согласно реальному согласию. Facebook App Events и Meta Audience Network adapter — разные компоненты.
5. Обязательный рекламный формат — **rewarded**. Interstitial и banner подключай по продуктовым правилам конкретной игры; их отсутствие само по себе не блокирует релиз. Отключённые пользователем форматы не создают/инициализируют placements, не загружаются и не показываются, не блокируют readiness; общий MAX SDK нужен rewarded. Уже согласованные и работающие форматы сохраняй, если пользователь их не отключил. Через панель переиспользуй/создай Android-блоки нужных форматов, сохрани привязку к игре и формату. **Настрой mediation-сети панели**, а не только MAX units: стандартный набор этого скилла — AdMob, Unity Ads, Mintegral, Pangle; явный набор текущего проекта имеет приоритет. Переиспользуй/создай приложения и placements каждой сети, свяжи реальные IDs с каждым поддерживаемым форматом MAX, установи совместимые official adapters и проверь resolved native dependencies. Для контрактов читай [references/superleo-ads.md](references/superleo-ads.md); merge existing settings обязателен. Недоступный provider сохраняется отдельным незавершённым шагом; остальные сети продолжаются. Наличие MAX unit без сетевых настроек/адаптеров не завершает этот этап. Подтверди успешный MAX init и native privacy result; подключи ready/load/show/error/close/revenue включённых форматов. Reward — только по реальному reward callback, однократно и с durable save; проверь correlation, долгий показ, background/resume, close без reward и восстановление позднего callback по [references/sdk-validation.md](references/sdk-validation.md). Banner учитывает safe area, inter — паузы/ограничения игры. Отсутствующие продуктовые правила показов/наград вынеси конкретным предложением.
6. Для каждого денежного получателя выбери **один** источник ad revenue и IAP revenue (включая SDK/backend adapters); для ad revenue: ручной или автоматический. Custom `ad_revenue` и специализированный `ReportAdRevenue` выполняют разные задачи; две специализированные денежные отправки за показ недопустимы. Проверь автосбор установленного SDK. `RevenueAutoTrackingEnabled` относится к покупкам и не доказывает отключение автоматического ad revenue.
7. Прочитай IAP-часть [references/play.md](references/play.md), [references/superleo-iap.md](references/superleo-iap.md) и [references/server-iap.md](references/server-iap.md). Отличай платежи от покупок за игровые монеты. После согласования каталога переиспользуй/создай товары Play **и** зарегистрируй эту игру, store mappings и награды в Multicast через панель. Подключи authenticated runtime validation SDK/мост этой игры: pending → проверка сервером → сохранённая награда и server ledger → claim/confirmation/recovery. Нельзя закрывать этап покупок прямым созданием SKU в Console при пропущенном backend. Добавь доступный игроку магазин со всеми согласованными товарами и реальными ценами; проверь его через обычный интерфейс актуального билда. Подтверди обработку отказов, replay/restore, sandbox и отсутствие дублей денежного revenue. Раздельно сохраняй регистрацию, runtime wiring, локальные тесты и реальную license-test транзакцию.

## Сборка и внутренний тест

1. Прочитай Android/Play-часть [references/play.md](references/play.md); для MCP onboarding/staging/upload/testers/release — [references/superleo-play.md](references/superleo-play.md). Доступность проверяй и по backend catalog, и по worker health/commands. `confirm:true` и точные строки подтверждения заполняются агентом в рамках уже разрешённого internal. Сверь package name, upload key/Play App Signing, version name/новый versionCode, target API, разрешённую Billing Library, 64-bit и 16 KB для всех `.so`. Актуальные требования проверяй официально при каждом релизе; снимок Devour не является вечной гарантией.
2. Подготовь необходимые выбранному треку записи Console и формы данных/рекламы по фактическому поведению игры/SDK. Подготовь тексты и обязательное оформление страницы: иконку, feature graphic и геймплейные скриншоты с подписями через внутренний генератор изображений. Следуй [references/store-assets.md](references/store-assets.md); используй кадры настоящей игры и отдельные render-акценты, стиль подписей выбирай под проект. Проинвентаризируй фактическую форму: все required/starred/conditional поля и все присутствующие визуальные категории, включая Phone, 7-inch, 10-inch tablets и прочие устройства. Заполни всю применимую визуальную часть и обязательные поля; готовые phone/icon/feature не закрывают tablet-поля. До завершения дождись загрузок, сохрани, перезагрузи и перечитай каждое поле с количеством, порядком и размерами assets по native Console evidence. Пустое применимое поле, pending upload, несохранённое изменение, ошибка или неизвестное блокируют завершение. Не отмечай формы выполненными при отсутствии данных владельца.
3. Собери подписанный **release AAB** воспроизводимым способом проекта. Если существующий сценарий собирает только WebGL/другую платформу, реализуй подходящую Android build entry point: проверка модуля, effective package name, сцен, SDK/ARM64/версии и безопасного доступа к upload key перед сборкой. Существующую чужую цепочку подписи не заменяй. Назначь и проверь launcher icon/имя приложения по [references/store-assets.md](references/store-assets.md): иконка в Console не меняет default/legacy/round/adaptive icons внутри AAB. Проверь их ресурсы в итоговом артефакте; отсутствие соответствия карточке блокирует загрузку. Проверь merged manifest/native dependencies, убери debug grants/заглушки. Сохрани путь, SHA-256, versionCode, package name и публичный fingerprint upload-сертификата. Проверяй ads на test devices, платежи — у license testers.
4. Выполни подходящие сценарии [references/verification.md](references/verification.md). Для первоначального включения Play Billing опубликуй подходящий billing-enabled AAB в **internal**: сохранённый draft не доказывает готовность настройки продуктов. Это входит в уже разрешённый internal-процесс. Заверши согласованный каталог/игру, собери финальный AAB с новым versionCode и выпускай именно его. Не раздавай тестерам незавершённый bootstrap-релиз.
5. Выпусти final AAB в **internal**, проверь трек/versionCode после записи. Настрой указанную владельцем группу, а по умолчанию — все существующие непустые списки текущего аккаунта с readback каждого. Запрашивай состав только при отсутствии списков или неясном доступе; новые адреса не придумывай. Верни opt-in ссылку. Установи из Play и проверь доступные сценарии. Недоступное устройство/кабинет — статус «ожидает проверки» с точным шагом, не «проверено».

После сбоя внешней записи сначала перечитай состояние по package name/ID/версии, затем решай, нужен ли повтор. Не создавай дубликаты после таймаута. Ошибку доступа не обходи придуманным API или чужим приложением: запиши ограничение, продолжи независимую подготовку.

## Видео-креативы и playable

В комплект подготовки входят **три разных обработанных видео** и **рабочий HTML5 playable**. Не ограничивайся сценариями, промптами или существующим прототипом. Прочитай [references/marketing-creatives.md](references/marketing-creatives.md) и [references/playable-contracts.md](references/playable-contracts.md): осмотри игру, запиши настоящий геймплей, смонтируй и отсмотри видео; выбери подходящий фрагмент игры, перенеси механику и ресурсы, собери варианты под сети и проверь touch/CTA/lifecycle/offline. В Piggy Payday поручен первый стол; в следующей игре агент выбирает подходящий понятный фрагмент по её механике, не переносит столы/копилки автоматически. Визуальные акценты/обложки при необходимости создавай внутренним генератором; игровой видеоряд остаётся записью игры. Сохраняй исходники, параметры и manifest вне переносимого архива скилла.

Обычные internal и production используют реальные рекламные блоки и production-окружения SDK. Название трека не включает тестовую рекламу: не добавляй устройство автоматически в MAX test devices и не используй QA build entry point для store-релиза. Перед загрузкой проверь actual version/compile defines/SDK config самого итогового AAB; production не содержит `PIGGY_INTERNAL_TESTING`, Adjust sandbox, sample ad IDs или автоматический GAID test-device lookup. Наличие зарегистрированных ID не доказывает production-режим.

Кнопка «принудительно показать rewarded в HUD» показывает сам оффер, обходя продуктовый таймер и скрывающий его tutorial gate. Она не переключает MAX в test mode, не отключает аналитику и не выдаёт награду. Окно нажатия начинается после возврата на HUD и готовности рекламы; загрузка имеет видимый статус. Проверь реальный pointer/raycast по иконке, таймеру и video badge, включая незавершённый tutorial: видимый оффер должен принимать ввод. Только completed reward callback выдаёт награду. Отдельная явно запрошенная рекламная QA-сборка использует вручную зарегистрированное тестовое устройство и подтверждённый native SDK test mode. Локальный Editor fixture изолируется от SDK/телеметрии и не попадает в player build. Разделяй проверку HUD, конфигурацию production и реально подтверждённые показы на устройстве.

## Версии каждого нового билда

Перед сборкой перечитай максимальный versionCode и последнюю versionName из всех треков и App bundle explorer, а также локальные manifests. Каждый НОВЫЙ AAB для internal, closed/open testing или production повышает И versionName, И versionCode. Нельзя публиковать 1.3.0 (4), затем новый билд 1.3.0 (5). Допустимы 0.0.1 (1), 0.0.3 (3), 0.1.0 (7); номер сборки не обязан совпадать с patch-компонентом. Без заданной пользователем версии повышай patch; заданная пользователем версия имеет приоритет и должна быть выше предыдущей. Установи значения в движке, проверь их в manifest именно подписанного AAB и в Console после обработки. Если версия/номер не выросли, останови загрузку и исправь сборку. Перенос неизменного AAB/SHA-256 между треками сохраняет versionName и versionCode; ради такого переноса не пересобирай игру.

Если владелец поручил обновлять одновременно internal и production, сохрани это в профиле игры как `release.update_tracks: ["internal", "production"]` и выполняй оба трека при каждом следующем релизе в рамках этого поручения. Собери один production AAB с новой версией и номером, выпусти его в internal и отправь этот же AAB в production. Успешный internal не завершает такой релиз: перечитай отдельно оба трека, подтверди одинаковые versionName/versionCode и SHA-256, а для production заверши отправку на review. Не пересобирай и не повышай версии отдельно ради второго трека. Если нужный AAB уже в обоих треках, проверь статусы вместо создания дубликата. Пока Google проверяет production, указывай новую версию как In review, отдельно от прежней публичной версии; одобрение и публикацию не обещай заранее.

## Результат

Скилл выполняет интеграцию под ключ в основной игре: устанавливает SDK, подключает события и интерфейс, проверяет callbacks и собирает Android. Проверки соразмерны включённым функциям: для каждого открытого gate укажи конкретное доказательство и следующий шаг, не расширяй релиз до общего аудита движка. Сохранённый ключ, зарегистрированный блок, изолированный прототип или выключенный bridge не означают завершённую интеграцию. Сохрани профиль/журнал с отдельными статусами кода, конфигурации, сборки, проверки устройства и Console. Каждый этап требует собственного manifest и реальных доказательств; успешный независимый этап не закрывает ожидающий доступ к стороннему сервису. Listing закрывается только после полного field-by-field save → reload → readback gate по [references/verification.md](references/verification.md). Приложи ссылки/пути, созданные сущности и согласованные товары без секретов управления. Финальный ответ: что готово, какой versionCode находится в internal, что реально проверено и какие действия остались. Production не входит в результат по умолчанию.

**Всегда выводи созданные и подключённые данные**, даже при незавершённом релизе, по [references/handoff.md](references/handoff.md): AppMetrica app ID/SDK API key, Adjust SDK app token/Android package/окружение, MAX приложение и IDs включённых форматов; отключённые interstitial/banner явно пометь вне scope. Отдельная таблица показывает сети mediation, их app/placement IDs по форматам и что реально сохранено в MAX, установлено в сборке и проверено на устройстве. Сохрани полный отчёт этой игры; не ограничивай итог фразой «сервисы подключены» или одной ссылкой на профиль. Доступы управления и пароли не являются SDK идентификаторами и в ответ/переносимый архив не входят.

Приложи три финальных MP4, playable HTML/ZIP по сетям, manifest с исходниками/SHA-256 и краткое описание механики/сюжетов. Разделяй локальную проверку и принятие рекламной сетью. Готовые рекламные материалы не означают их загрузку или запуск кампании.
